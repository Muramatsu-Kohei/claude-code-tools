# 作業ログへの記録

このセッションでここまでにやったことを振り返り、`worklog` に記録してください。
git 操作・ファイル編集・テスト実行は**行わないこと**。このコマンドは記録だけを担当します。

## 手順

1. このセッションの会話を振り返り、以下を整理する。
   - **一言要約**: 何をしたか。40〜60 文字程度。成果物や変更対象が分かる具体的な書き方にする。
     「修正を行った」「作業を進めた」のような中身のない表現は禁止。
   - **やったこと**: 完了した作業を 1 行ずつ。細かすぎる手順ではなく、後から見て意味が分かる粒度にまとめる。
   - **次にやること**: 未完了の作業・残った課題を 1 行ずつ。無ければ省く。
   - **次回の始め方**: 次のセッションがこの続きを再開するための具体的な指示。
     対象ファイルの絶対パス・確認すべきコマンド・判断が保留になっている点を含める。
     残り作業が無い場合は省く。

2. `worklog add` を実行して記録する。`ARGUMENTS` に補足指示があればそれを反映する。

```
node C:/claude/ClaudeCode/claude-worklog/worklog.js add --via wrap \
  --summary "<一言要約>" \
  --done "<やったこと1>" --done "<やったこと2>" \
  --next "<次にやること1>" \
  --handoff "<次回の始め方 1行目>" --handoff "<次回の始め方 2行目>"
```

- `--done` `--next` `--handoff` は繰り返し指定できる。`--handoff` は指定順に改行で連結される。
- 1 つのリポジトリに複数のツールが同居していて、**このセッションがどのツールの作業だったかが
  変更ファイルから読み取りにくい**場合(調査だけで終わった、複数ツールにまたがった等)は
  `--scope <ツール名>` を付ける。ツール名はリポジトリ直下のディレクトリ名
  (例: `claude-worklog`、入れ物の下なら `tools/tool-d`)。省略時は変更ファイルから
  自動判定されるので、通常は付けなくてよい。
- セッション ID は環境変数から自動で解決されるので `--session` は不要。
- 値に改行を含めてはいけない。改行が必要なら項目を分ける。
- **値にバックティック(`` ` ``)と `$` を使わないこと。** PowerShell ではバックティックが
  エスケープ文字として解釈され(`` `n `` が改行になるなど)文字列が壊れる。bash でも
  二重引用符内のバックティックはコマンド置換になる。コマンド名やパスは引用符で囲まず素のまま書く。
- Windows では 1 行で書くか、シェルに合った継続記法を使う。

3. 記録した内容を 3〜5 行で画面に示す。長い再掲は不要。

$ARGUMENTS
