# Claude アカウント分離：設計と運用

組織アカウントと個人アカウントを使い分けるとき、Claude Code の**何が分かれて、何が分かれないか**。
`account-guard` がなぜこの形になったかの設計根拠でもある。

| 何 | どこ |
|---|---|
| アカウント別のガード | `account-guard/` |
| 使用量のアカウント別記録・集計 | `usage-tracker/`（`collect.js` `guard.js` `analyze.js`） |
| 分離前に貯めた使用量ログへのアカウント遡及付与 | `usage-tracker/migrate-account.js`（§3.5 の一度きりの移行用） |
| 作業ログのツリー隔離 | `claude-worklog/`（`restrictedTrees` 設定） |
| 5 時間枠 ping のアカウント別状態 | `claude-window-keeper/` |

---

## 1. 前提となる事実

### 1.1 ほぼ全部ローカルにある

`~/.claude/` の中身:

| もの | 実体 | スコープ |
|---|---|---|
| セッション履歴 | `projects/**/*.jsonl` — セッションごとに 1 ファイル。使い込むと数百ファイル・数百 MB になる | ローカル |
| 自動メモリ | `projects/<dir>/memory/` | ローカル・ディレクトリ単位 |
| `CLAUDE.md` | `~/.claude/CLAUDE.md` | ローカル・**全セッション共通** |
| skills / agents / plugins / commands | `~/.claude/` 配下 | ローカル・全セッション共通 |
| 設定・フック | `~/.claude/settings.json` | ローカル・全セッション共通 |
| worklog | `~/.claude/worklog/*.ndjson` | ローカル・ツール横断 |
| usage-tracker | `~/.claude/usage-tracker/usage.jsonl` | ローカル |
| **アカウント紐づけ** | `.credentials.json` — 1 KB に満たない 1 ファイル | これだけ |

**結論: アカウントを失っても消えるのは利用権だけで、ファイルは 1 バイトも消えない。**
別アカウントでログインし直せば履歴もメモリも設定もそのまま読める。

### 1.2 サーバ側にあるもの（＝アカウントに紐づく）

- 契約（利用権）そのもの
- claude.ai の Web 会話、公開した Artifacts、クラウド実行セッション、スケジュール実行エージェント
- **組織管理者からの可視性** — 使用量。プランによっては会話内容のエクスポート

### 1.3 `/login` の挙動

- `.credentials.json` は 1 つだけ。**同時にアクティブなログインは 1 つ**
- `/login` で入れ替わるのはこのファイルだけ。他の設定資産はすべて共有されたまま
- **マシン全体に即座に効く** — 並行して動いている他のセッションにも影響する

## 2. 何が危険か（方向によって相手が変わる）

### 組織のコード → 個人アカウント：**NG（絶対）**

相手は「組織」（守秘義務違反）と「Anthropic」（個人プランは学習利用の設定次第）。
自分の一存では正当化できない。

### 個人のコード → 組織アカウント：**推奨されないが、自分でリスクを取れる**

Anthropic との関係ではほぼ問題にならない（組織が払った座席を組織のメンバーが使っているだけ）。
問題になる相手は所属組織で、実害の経路は 2 つ:

1. 管理者から使用量が見える（プランによっては内容も）
2. **成果物の帰属** — OSS 公開したくなったとき、「業務アカウントで全部作った」事実が反証を難しくする

「退職で消える」は**当てはまらない**。§1.1 のとおりファイルはローカルに残る。

### 強度の差

- 「組織のコードを個人アカウントで触らない」= **絶対**（相手の情報だから）
- 「個人のコードを組織アカウントで触らない」= **推奨**（自分の資産の話だから）

同じ厳しさで運用する必要はない。ただし**公開する気のあるコードだけは分けておく**。

## 3. アカウントを分けても自動では分かれないもの

`/login` はトークンだけを入れ替える。以下は**アカウントに関係なく共有される**。

### 3.1 セッション開始時に自動注入されるもの

無操作で文脈に載るので、`--resume` を避けるだけでは防げない。

| もの | スコープ | リスク |
|---|---|---|
| `~/.claude/CLAUDE.md` | 全セッション共通 | 組織固有の記述を書くと個人アカウントにも載る |
| `projects/<dir>/memory/MEMORY.md` | ディレクトリ単位 | 保護ツリーに入れば自動で載る |
| worklog の引き継ぎメモ | リポジトリ単位 | 「他に未完の作業があるツール」を列挙する |

worklog の索引を組み立てる `scopeIndex()` の**走査範囲は 1 つの ndjson ファイル＝1 つの
git リポジトリの中**に閉じている。別ツリーのリポジトリは別キーになるため、**自動注入で
保護ツリーの内容が載ることはない。**

混ざる経路は**手動実行のときだけ**——`worklog today`（既定で全キー横断）、`worklog list --all`、
`worklog export --all`。ここは `restrictedTrees` 設定で塞いだ。

書き込みは制限していない。保護ツリーで組織アカウントを使う分には今までどおり記録される。
**制限したのは読み出しだけ**で、これは §2 の「強度の差」——守るのは相手の情報であって
自分の記録ではない——をそのまま反映している。

### 3.2 履歴はディレクトリ単位で、アカウント単位ではない

`projects/` のキーは**作業パス**であってアカウントではない。
個人アカウントで保護ツリーに入り、過去セッションを `--resume` すると、
**その履歴の中身が個人アカウントのトークンで再送される。**

### 3.3 共有される設定資産

`skills/` `agents/` `commands/` と MCP のトークンキャッシュはグローバル。
組織向けに書いたスキルに内部情報があれば、個人アカウントのセッションでも読み込まれる。

### 3.4 ディレクトリは砂場ではない

どこで作業していても Read も Bash も保護ツリーに到達できる。
**ディレクトリ固定は規約であって技術的な壁ではない。**

### 3.5 使用量の記録はアカウントを区別しない

`usage-tracker/collect.js` が追記する `row` には、元々**アカウント識別子がなかった**。
切り替えると組織の `five_pct: 80` と個人の `five_pct: 5` が 1 本の時系列に混ざり、
`guard.js` の閾値判定も `analyze.js` の推定も壊れる。
→ **アカウントを分けるなら `row` に識別子を足すのが前提作業。**

`row` に `acct` を追加し、差分判定の state を `collect-state-<アカウント>.json` に分けた。
`guard.js` は自分のアカウントの state だけを見る。`analyze.js` は既定で現在のアカウントに
絞って集計し、`--account all` のときだけ混ぜる（そのときは推定値が意味を持たない旨を警告する）。

**識別子を足すだけでは足りなかった。** 実装して分かった壊れ方:

- `analyze.js` の `weekWindowStarts` は「`seven_reset` が変わった＝週次リセット」と解釈するため、
  **アカウントの切り替えを新しい週と数える**。既定のレポートは直近 1 週分なので、
  放置すると「最後に切り替えて以降の数行」しか描かなくなる
- `guard.js` の発火済みフラグはセッション単位だが枠のリセット時刻でしか同一性を見ておらず、
  セッション途中で `/login` すると誤って抑止／再通知が起きる。フラグに `acct` を持たせて解決
- `claude-window-keeper` の `state.json` も `lastPing` を 1 本しか持たず、切り替え直後の ping を
  「送信済み」と誤判定していた。5 時間枠の開始時刻を固定するというツールの目的が崩れる

**時系列データを持つツールは、アカウントをまたぐと「同一性の判定」が軒並み壊れる。**

## 4. ガードの設計

### 4.1 使える機構

| 機構 | 効果 | 可否 |
|---|---|---|
| `SessionStart` フックが `{"continue": false, "stopReason": "..."}` を返す | — | **効かない。** 公式ドキュメントで `SessionStart` は "Context only / No blocking or decision control" と明記。exit code 2 も stderr を表示するだけでブロックしない |
| `PreToolUse` フックが `hookSpecificOutput.permissionDecision: "deny"` を返す | ツール単位で拒否 | **確定。実地で動作を確認済み** |
| `CwdChanged` フック | セッション途中の `cd` を捕捉 | **実在する。** ただしブロック可否は未確認なので警告用途にとどめた |
| `permissions.deny` に `Read(<保護ツリー>/**)` 等 | パス単位の静的拒否 | 記法は確定。ただし静的でアカウント条件を表現できないため不採用（§4.5） |
| `forceLoginOrgUUID`（managed settings 専用） | 認証アカウントの組織を強制 | 確定 |

**この表が設計を決めた。** ブロックできるのは `PreToolUse` だけなので、実際の防御はそこに置き、
`SessionStart` と `CwdChanged` には警告を出す役割だけを持たせた。

### 4.2 核心的な制約：identity は取れない（が、プラン種別は取れる）

フックに渡る入力（stdin JSON）に**アカウント情報は含まれない**。
`.credentials.json` にも identity フィールドはない（§4.3 に構造）。
したがって「どのアカウントか」を知る方法はない。

`permissions.deny` は静的なので「個人アカウントのときだけ拒否」を表現できない。
`forceLoginOrgUUID` はマシン全体に効くため、ディレクトリ別条件にできない
（設定すると個人アカウントが一切使えなくなる）。

**ただし `subscriptionType`（プラン種別）は取得できる。**
組織 = Team、個人 = Pro / Max なら、identity がなくても判別条件として成立する。

### 4.3 採用した判別方法：`subscriptionType` でプラン種別を見る

#### `.credentials.json` の構造

```json
{
  "claudeAiOauth": {
    "accessToken":  "<長い文字列>",
    "refreshToken": "<長い文字列>",
    "expiresAt": 1785664958179,
    "refreshTokenExpiresAt": 1786278760179,
    "scopes": ["user:file_upload", "user:inference", "user:mcp_servers", "user:profile", "..."],
    "subscriptionType": "team",
    "rateLimitTier": "default_raven"
  }
}
```

**`accountUuid` / `organizationUuid` / `emailAddress` のような identity フィールドは存在しない。**
「どのアカウントか」を直接知る手段はない、が確定。

一方 `subscriptionType` は組織アカウントなら `"team"`、個人なら `"pro"` / `"max"` になる。
**「どのアカウントか」は分からなくても「Team かどうか」は分かる**ため、2 アカウント構成なら
判別条件として十分。`rateLimitTier` も値は変わるが、意味が不透明で同じプランでも契約内容に
よって変わりうるため使わない。

利点:

- **アカウント属性なのでトークンのリフレッシュでは変わらない**
- 自己申告に頼らないので、ランチャーを経由せず素の `claude` を叩いても止まる
- 環境変数の設定忘れという事故が原理的に発生しない

制約:

- 文書化されていない内部フィールド。Claude Code の更新で構造が変わりうる → **読めなければ安全側（ブロック）に倒す**
- 判別できるのはプラン種別であって identity ではない。個人側も Team 契約にすると機能しない

判別不能（`null`）もブロック対象にしている。フィールドが廃止されたときに
**黙って素通しになるより、止まって気づけるほうがよい**ため。

#### 設計上の要点

| 論点 | 決定 | 理由 |
|---|---|---|
| 登録先 | `PreToolUse` でツール単位に拒否 | ブロックできる機構が他にない（§4.1）。`SessionStart` / `CwdChanged` は警告のみ |
| 保護ツリー | `~/.claude/account-guard/config.json` に外出し | 複数ツリー・複数許可アカウントに対応するため |
| 判定対象 | cwd に加えてツールの**操作対象パス**も見る | ツリー外から絶対パスで触りにいく経路を塞ぐため |

**判定対象では一度誤った。** 当初は `tool_input` を丸ごと文字列化して走査していたところ、
この文書を編集しようとして拒否された（当時は保護ツリーの実パスが本文に書かれていた。
現在は一般化して残していないので、いま同じ現象は再現しない）。保護ツリーの
ファイルには触れていないのに止まるのは明確な誤りなので、`Read` / `Edit` / `Write` などは
パス引数だけを見るように直した。`Bash` / `PowerShell` / `Agent` はコマンドや指示文の全体を
見る（パスの位置が決まっておらず、「読め」という指示自体を止めたいため）。

**誤検知はガードの寿命を縮める。** 日常の邪魔になれば外したくなり、外せば守りはゼロになる。
拒否の範囲は「守るものが実際に増える操作」に限る。

### 4.4 登録方法

`~/.claude/settings.json` に登録する。ひな形は `account-guard/hooks-snippet.json`。

```json
{
  "hooks": {
    "PreToolUse": [
      {
        "matcher": "*",
        "hooks": [{ "type": "command", "command": "node <path>/account-guard/account-guard.js", "timeout": 5 }]
      }
    ],
    "SessionStart": [
      { "hooks": [{ "type": "command", "command": "node <path>/account-guard/account-guard.js", "timeout": 5 }] }
    ],
    "CwdChanged": [
      { "hooks": [{ "type": "command", "command": "node <path>/account-guard/account-guard.js", "timeout": 5 }] }
    ]
  }
}
```

**実際に止まるのは `PreToolUse` だけ**で、残り 2 つは気づきを早めるための警告。

`matcher` は `"*"`（全ツール）にする。ツール名を列挙する形だと、
**名前を事前に知りようがないツール**——MCP サーバーが提供するファイル操作ツールなど
——がフックに届かない。実装側は「知らないツールは引数全体から絶対パスの形を拾う」
という作りで最後の砦にしているのに、列挙式の matcher はその砦の手前で素通りさせる。
全呼び出しで node を起動するコストはかかるが、取りこぼしの危険とは釣り合わない。

**設定変更は稼働中のセッションにも即座に効く。** 再起動は要らない。

**サブエージェント経由でも拒否される。** サブエージェントのツール呼び出しにも同じ
`PreToolUse` が挟まるため、委譲は抜け穴にならない。ここが素通しなら「サブエージェントに
読ませる」だけでガードを迂回できてしまうので、実際に確かめてある。

§3.4 の「ディレクトリは砂場ではない」に対する答えがこの `PreToolUse` 層そのもので、
cwd だけでなくツールの操作対象パスも見ることで、ツリー外から絶対パスで触りにいく経路も塞いだ。

### 4.5 採用しない案

| 案 | 却下理由 |
|---|---|
| 設定ディレクトリを分ける | 同時起動が要件でないなら利点がなく、設定資産の分断リスクだけが残る（§5.1） |
| `forceLoginOrgUUID` を managed settings に書く | マシン全体に効き、個人アカウントが使えなくなる |
| `permissions.deny` 単体 | 静的なのでアカウント条件を表現できない |
| 起動方法を環境変数で宣言させ、パスと突き合わせる | 自己申告なので設定忘れで素通しになる。`subscriptionType` が使えなくなった場合のフォールバック候補としてのみ残す |

（かつてここに「statusline に現在のアカウントを表示する」を、起動バナーが同じ情報を
より正確に出しているという理由で並べていた。その前提が誤りだと分かったので §4.6 で採用した。）

### 4.6 statusline に現在のアカウントを出す（§4.5 からの方針転換）

**却下していた理由が事実として誤っていた。** 起動バナー `Opus 5 · Claude Max · <組織名>` は
1 つの情報源から出ているように見えて、実際は 2 系統の寄せ集めになっている。

| バナーの構成要素 | 読み元 | 更新のタイミング |
|---|---|---|
| プラン名（`Claude Max`） | `~/.claude/.credentials.json` の `subscriptionType` | 即座（ファイルの mtime を見ている） |
| 組織名 | `~/.claude.json` の `oauthAccount.organizationName` | `profileFetchedAt` から **24 時間**キャッシュ |

`swap` は `.credentials.json` しか書かない。したがって切り替えた直後は
**プランだけ新しく、組織名は前のアカウントのまま**という食い違いが最大 1 日続く。

2026-08-16 に無編集の実測で確認した。個人（Max）アカウントで動かしているのに、TTL が切れる
までの間バナーは組織アカウント名を出し続け、TTL 切れ後の起動でようやく
`organizationType` が `claude_team` → `claude_max` に、組織名も個人のものに変わった。

つまりバナーは「アカウントを取り違えていないか」の確認に使えない。むしろ **Team のつもりで
個人枠を溶かす取り違えを、それらしい表示で後押しする**。却下時に挙げていたコスト
（実稼働版とリポジトリ版に同じ機能を入れ続ける保守と、stdin だけで完結していた表示ロジックに
初のファイル I/O が加わること）は今も残る。しかし判断の前提だった「バナーのほうが正確」が
崩れた以上、そのコストと引き比べる相手がいない。

実装は `claude-statusline/statusline.js` の `readAccountSlot()`。`~/.claude/accounts/.current`
を読んで `@<スロット名>` を先頭グループに出す。account-guard を使っていない環境では
ファイルごと無いので何も出ない（statusline 単体の利用者に影響しない）。

**限界も同じ場所に書いてある。** `.current` は「前回このツールが切り替えた先」の来歴であって、
現在のログインの証明ではない。`swap` を通さず `/login` し直せば古いまま残る。
バナーより新しいというだけで、絶対的な真実ではない。

## 5. 運用ルール

**アカウントはディレクトリツリーに固定する。** git の author をパスで決めているのと同じ発想。

| ツリー | アカウント | git author |
|---|---|---|
| 保護ツリー | **組織のみ**（`account-guard` が強制する） | 組織メール |
| それ以外 | どちらでもよい | noreply |

**非対称なのは意図的。** 組織のコードを個人アカウントに渡すのは相手の情報を持ち出すことなので
絶対に避ける（§2）。逆向きは自分の資産の話で、リスクを取るかは自分で決められる。

保護ツリーに入るときだけ組織アカウントに切り替える。忘れても `account-guard` が最初のツール
呼び出しで止めるので、気づかずに読み込ませることはない。

### 5.1 切り替え方式：credentials スワップ

`/login` はブラウザ OAuth を毎回踏むうえ、マシン全体に即時に効くので稼働中の別セッションも
巻き込む（§1.3）。切り替えの手間を下げる方式を 2 つ比較した。

| | A: credentials スワップ | B: `CLAUDE_CONFIG_DIR` 分離 |
|---|---|---|
| 同時起動 | 不可 | **可能**（プロセス単位でアカウントが決まる） |
| 設定・メモリ・履歴 | **一切変わらない** | junction で共有しない限り分かれる |
| OAuth 再実行 | 放置すれば必要 | 同左 |
| 実装量 | 小 | 中（junction 構成 + ランチャー 2 本） |

**A を採用した。理由は「同時に 2 つ走らせる必要がない」の 1 点。** 同時起動が要件でないなら、
B が持つ唯一の優位が消え、代わりに設定資産の分断リスクだけが残る。A で変わるのは
`.credentials.json` **1 ファイルだけ**で、CLAUDE.md・memory・skills・agents・履歴・
worklog・usage-tracker はすべて現状のまま。セッションを切る必要もない。

なお `CLAUDE_CONFIG_DIR` を空ディレクトリに向けて起動すると `Not logged in` になり、
新規に作られるのは `projects` / `sessions` / `backups` / `.claude.json` の 4 つだけだった。
CLAUDE.md や skills は junction で共有できる。**つまり「共有できないから」は却下理由として
成立しない。却下は維持するが、根拠は「同時起動が不要だから」。**
並列運用が必要になったら、A を捨てずに B を上に足せる。

実装:

- `~/.claude/accounts/<名前>.json` に退避
- `swap <名前>` が「現在を退避 → 指定を復元」
- `account-guard` は保険として維持（切り替え忘れは保護ツリーの初回ツール呼び出しで止まる）

**残るリスクは平文トークンが増えること。** 元々 1 本が平文なのでリスクの質は変わらないが、
数は増える。退避先を `~/.claude` 配下にすれば保護レベルは同一。

> **本数は実装でさらに増えた。** credentials に identity フィールドが無い以上、同一プランの
> 別アカウント同士は原理的に判別できない。取り違えた上書きで唯一のバックアップが消えるのを
> 防ぐため、既存スロットを上書きする前に旧内容を `accounts/.replaced/` へ控える実装にした
> （スロットごとに 2 本まで。上限を超えた分だけ落とし、落とす順は失効済みから）。
> 「失効しているから」で無条件に消す実装は取りやめた——退けた直後の控えがその場で消え、
> 時計がずれた環境では失効していない控えまで巻き添えになるため。
> **判断で守れないものを構造（復旧可能性）で守る**、というトレードオフ。

`refreshTokenExpiresAt` があるので、退避したトークンがいつまで使えるかは事前に分かる
（猶予は数週間程度）。`swap` はこの値を読んで残日数を表示する。

#### 規約上の確認

**複数アカウントの保持を禁じる条項は存在しない**（Consumer Terms と Usage Policy を実読）。
禁止されているのは「認証情報を他人と共有すること」("You may not share your Account login
information, Anthropic API key, or Account credentials with anyone else")、「BAN 回避のための
別アカウント」、「複数アカウントでの悪意ある活動の調整」で、いずれも本件に当たらない。
自分のマシン内で自分のトークンをファイルとして保管する行為は共有ではない。
`CLAUDE_CONFIG_DIR` も Claude Code が公式に提供する環境変数であって抜け道ではない。

**残る相手は所属組織。** 組織の座席は組織との関係なので、組織側の規程が別に効く。

### 5.2 5 時間枠の扱い：窓は「揃える」

#### 何が問題か

`claude-window-keeper` の ping は**ログイン中のアカウントにしか打てない**（送信手段が
`claude -p` だけなので原理的にそうなる）。結果、片方だけが「5 時間おきの時刻表」に乗り、
もう片方はどこにも乗らない。切り替えた側の窓は**切り替えた瞬間**に開くため、2 つの時刻表が
かみ合わず、作業の途中に待ち時間が生まれる。

#### 運用：作業を始める直前に、両方の窓を開ける

```
アカウント A に切り替え → ping 1 発 → B に戻す → ping 1 発 → 作業開始
```

窓を開けた時点から、2 アカウント合計ぶんの作業が穴なしで入る。
単一アカウント時代の「窓の終わりぎわに入って 2 枠を地続きにする」使い方は**不要になる**。
1 サイクル内で 2 つの枠を繋げられ、そちらで既に地続きになるため。

1 枠を使い切るのにかかる実作業時間はプランと作業内容で変わる（同じアカウントでも窓ごとの
ばらつきが大きい）。`usage-tracker/analyze.js` が `(acct, five_reset)` で窓を切り出して
消費速度を出せるので、**自分の実測値で計画する**。

#### `claude-window-keeper` には手を入れない

公開済みの単体ツールなので、依存の向きを **swap → window-keeper** にする。両窓オープンは
swap 側のコマンドとして実装し、中身は既存の ping スクリプトを、アカウントを入れ替えながら
2 回呼ぶだけにする。単一アカウント利用者の既定動作は一切変わらない。ping の state は既に
アカウント別に分かれている（§3.5）ので、そちらの改修も要らない。

**毎時タスクの解除も不要。** アクティブ側の時刻表を維持する働きは複数アカウントでも有効で、
両窓オープンと競合しない。非アクティブ側は作業ブロックの間に時刻表から外れるが、次のブロック
開始時に揃え直すので実害がない。

#### 禁止事項：タイマーから credentials を入れ替えない

認証の入れ替えはマシン全体に即座に効き、並行して動いているセッションを巻き込む（§1.3）。
バックグラウンドタスクが裏で swap すると、稼働中のセッションがターンの途中で別アカウントに
乗り換わり、保護ツリーにいればガードに拒否されて止まる。**両窓オープンは、キーボードの前に
いる前提の手動コマンドにする。**

### 5.3 両方の窓を開ける：`swap warmup`

§5.2 の「作業を始める直前に両方の窓を開ける」は、手でやると切り替えと ping を 4 回打ち分ける
ことになり、順番を間違えたり戻し忘れたりする。これをコマンド 1 つにする。

#### どこに置くか：`swap.js` のサブコマンド

`swap warmup` が `claude-window-keeper` の ping スクリプトを子プロセスとして呼ぶ。逆向き
（window-keeper 側に置いて swap を呼ぶ）にしない理由は、**warmup が複数アカウント所有者に
しか意味を持たない機能**だから。単一アカウントで window-keeper だけを使っている人から見ると、
自分が使えないツールがそこに同居しているのは違和感になる。切り替えの関心事は swap に寄せる。

ping を swap.js が自前で `claude -p` して済ませる案は採らない。window-keeper の state が
更新されず、次の毎時実行で ping が二重に飛んで窓が張り直るため（§3.5 と同じ壊れ方）。

#### 動作

1. 開始時のアカウントを記録する
2. 退避済みアカウントを一覧表示し、確認を取る
3. 各アカウントについて順に：`refreshToken` が失効していればスキップして警告、
   そうでなければ切り替えて ping を実行する。ping の出力はそのまま素通しする
4. **必ず開始時のアカウントに戻す**
5. アカウントごとの結果（成功 / 失敗 / スキップ）を一覧表示する

対象は退避済みアカウント**すべて**で、2 つとは限らない。開始時のアカウントは順番の**最後**に
回す（不変条件は finally で守るが、最後に置けば正常に終わった時点で既に戻っているので、余分な
切り替えが 1 回減る）。サブコマンドと同じ名前のスロットは `swap <name>` で復元できないため、
除外して理由を表示する。

呼び出しは `powershell.exe -NoProfile -ExecutionPolicy Bypass -File <ping.ps1>`。
ping スクリプトのパスは環境変数 `CLAUDE_WINDOW_PING`、無ければ swap.js から見た
`../claude-window-keeper/claude-window-ping.ps1`。どちらも無い場合に壊れるのは warmup だけで、
`swap` / `swap save` は動く（ping スクリプトを持たない人のため）。ただし `credentials.js` と
`subcommands.js` は swap.js と同じディレクトリに必ず要る。前者はアカウントの読み方をガードと、
後者はサブコマンド名の表を故障注入テストと共有しており、どちらも欠けると全コマンドが止まる。

#### 決めたことと理由

| 論点 | 決定 | 理由 |
|---|---|---|
| ping を打つ条件 | `-Force` を付けない | 5 時間未経過なら ping 側が SKIP する。既に開いている窓に打つ枠の無駄を避ける。判定基準が「前回 ping からの経過」であって「窓が実際に開いているか」ではないため、手作業で窓を開けた日は余分に 1 発飛ぶことがあるが、その程度は許容する |
| SKIP の見せ方 | ping の出力を素通しし、warmup 側では解析しない | SKIP は `return` で抜けるため終了コードで送信と区別できない。標準出力の文字列に依存すると、ping 側の表示を変えた日に黙って壊れる |
| 実行前の確認 | 既定で確認、`--yes` で省略 | warmup は切り替えを複数回行うので、稼働中の別セッションを巻き込む度合いが `swap` 単体より大きい |
| 自動実行の歯止め | 標準入力が TTY でなく `--yes` も無いときは中止 | §5.2 の「タイマーやフックから呼ばない」を仕様として担保する |
| 中断時 | 各 ping に 5 分のタイムアウト。中断されたら `swap <元の名前>` で戻せる旨を表示 | 1 つが固まったまま元のアカウントに戻れなくなる状態を作らない。強制終了までは保証できないので、戻し方を人に伝える |

不変条件は **「終了時のアカウント = 開始時のアカウント」**。ping が失敗しても、途中でエラーが
出ても守る。

#### 実装で決めたこと（2026-08-15）

| 論点 | 決定 | 理由 |
|---|---|---|
| 切り替えの呼び方 | `swap.js` 自身を子プロセスとして起動する | 切り替えの本体（`cmdSwap`）はガードのすべてを `fail()` = `process.exit(1)` で中止する前提で書かれており、戻り値も持たない。関数として呼ぶと 1 つのアカウントがガードに当たった時点でプロセスごと終わり、「片方が失敗しても残りは試し、最後に必ず戻す」が成立しない。ガードの文面を戻り値へ作り替える改修は、出力を 1 行ずつ検証している既存テストを丸ごと巻き込む。プロセス境界に閉じ込めれば exit code だけで成否が取れ、案内の文面はそのまま画面に流れる（ping を子プロセスとして呼ぶのと同じ形になる） |
| `--force` | 受け付けず中止する | `--force` は失効済み・判別不能・同一プランのガードをまとめて外すフラグで、`warmup` に付けると複数回行う切り替えのすべてに 1 回の同意で効く。特定のアカウントへ強行したいなら `swap <name> --force` を個別に実行すればよい |
| 戻る向きの切り替え | 開始時のアカウントへ戻る 1 歩だけ、内部で `--force` を使う（進む向きでは使わない） | 付けないと `max → team → max` のような並びで最後の 1 歩が「同一プランで別アカウントだと証明できない」ガードに当たり、開始時とは別のアカウントに乗ったまま終わる（不変条件が破れる。実装当初そうなっていた）。戻り先の退避はこの実行の最初の切り替えで `warmup` 自身が書いた内容そのもの（切り替えの前に必ず現在のログインを来歴のスロットへ退避する）なので、ガードが守っている「別アカウントの取り違え」は起こりえない。一度も切り替わっていなければ来歴を見て切り替え自体を行わないので、古い退避を掘り起こす経路にもならない |
| `--yes` の位置 | `--force` と同じく、引数のどこに置いても取り除く。`warmup` 以外に付けたら中止 | 位置を限定していた `--force` が「打った形と効く内容が食い違う」事故を起こした前例に合わせる。他コマンドで黙って捨てると、確認を省いたつもりのフラグが何にも効かないまま進む |
| 戻り先が決まらないとき | 来歴（`.current`）が未記録・読めなければ、切り替えを 1 回も行わずに中止 | 戻り先の名前が決まらない状態では不変条件を守れない。始めてから気づくと、戻す手段がないまま複数回の切り替えだけが残る |
| 終了コード | 失敗が 1 件でもあれば 1、スキップだけなら 0 | 失効した退避を飛ばすのは仕様どおりの動作であって、失敗ではない |
| 退避の健全性を見る範囲 | 切り替えて復元する対象だけ。既にログイン中のアカウントには掛けない | 判定材料は退避ファイル（`accounts/<name>.json`）で、これは最後に `save` した時点の内容。ping のたびにトークンはローテートするので、動いているアカウントの退避は古くなる。切り替えないのに退避を見て弾くと、いま有効な認証で開けるはずの窓を開けないまま `スキップ` で終わる（退避が開始時の 1 件しかない環境で踏む） |

サブコマンド名の表（`main()` が横取りする語）は `subcommands.js` に切り出し、故障注入
property test の操作列をそこから生成するようにした。表へ 1 行足せばテストの守備範囲に自動で
入るので、「新しいサブコマンドを足したらテストの操作列にも足す」という守られない規約が要らない。

### 5.4 保護を一時的に外す（`guard unlock`）

使用量リミットに当たったとき、あるいは保護ツリー内にあるが実体は保護対象でないディレクトリを
別アカウントで触りたいときに、**そのセッションに限って**保護を外す。使い方は
`account-guard/README.md` の「一時的に解除する」に書いた。ここには設計の判断だけ残す。

| 論点 | 決定 | 理由 |
|---|---|---|
| 置き場所 | `swap.js` ではなく `account-guard.js` のサブコマンド | swap の分岐は「`save` 以外の第一引数はアカウント名」なので、`unlock` を足すと同名スロットと衝突して予約語の追加が要る。加えて swap は認証情報を入れ替えるツールで、ガードの判定を変える操作とは責務が違う。解除状態を読むのはガード側なので、書く側も同じファイルにあれば定数と読み書きを共有でき、テストも既存のスイートに乗る |
| 解除の単位 | 保護ツリーではなく、その配下の任意のディレクトリ（既定は cwd） | `tree` は git の管理単位ではなくただのパスで、判定は前方一致。ツリー単位で解除すると、ルートに保護対象と非保護対象が混在している構成では全部が開く。それでは配下の 1 ツールだけを別アカウントで触ることができない |
| Claude 自身の解除 | 経路を分けて塞ぐ（承認ダイアログにはしない） | PreToolUse フックはユーザーの `!` 実行では発火しない（実測）。ダイアログは押せば通るので、もっともらしい理由を添えて要求されたときに流し読みで通る余地が残る。歯止めは「コマンドの遮断」と「状態ファイルへの書き込み拒否」の 2 層で、後者は前者をすり抜けて `unlocks.json` を直接書く経路を塞ぐ |
| 解除中の再解除 | 解除中のセッションでも `unlock` は拒否する | 延長・再発行ができると、ユーザーが範囲を絞って開けた意味がなくなる。この判定は解除フィルタより先に置く |
| 有効期限 | 設けない（セッションの終了で失効） | 用途は「リミットが回復するまでの数時間」。短い期限は用途の途中で切れて再解除を促し、「とりあえず解除」を習慣化させる。歯止めのつもりが逆に効く |
| 対象が複数あるとき | 全部が解除範囲の配下でなければ拒否 | `tool-a` だけを解除した状態で `tool-a` と `tool-b` を同時に触るコマンドが通る穴を塞ぐため |
| `--path` の形式 | ドライブ文字から始まる絶対パスのみ | 設定の `tree` はドライブ文字を落としても書き損じにならず、ドライブ不問・パス途中でも一致する広いルールになる（issue #6）。`tree` 側は過剰に拒否する向きの誤りで済むが、解除側で同じ緩さがあると**保護が外れる向き**に広がる |
| フェイルセーフ経路 | ガードが異常終了したときの縮小判定にも解除を反映する | 反映しないと「ガードが壊れている間だけ解除が無視されて詰む」穴が残る。状態を読めなければ従来どおり拒否側に倒す |

解除の状態は `~/.claude/account-guard/unlocks.json`（現に効いている解除）と `unlock.log`
（追記型の履歴）の 2 つ。前者は Claude からの書き込みを常に拒否する保護対象でもある。

## 6. コードでは守れない範囲

フックでもガードでも到達できないので、**設定資産を足すたびに手で確認するしかない。**

- **個人アカウント側のデータ学習利用設定** — Web の設定画面にある。アカウントを増やすたびに確認する
- **`~/.claude/CLAUDE.md` に組織固有の記述を書かない** — 全セッション共通なので、
  ここに書いた時点で個人アカウントにも載る。組織固有の指示はツリー内のプロジェクト
  `CLAUDE.md` に書くこと
- **`~/.claude/skills` `agents` の棚卸し** — グローバルに読み込まれるため、
  組織向けに書いたものが個人アカウントのセッションにも載る

**この 3 件は再発する。** skills / agents を新設したときと、アカウントを増やしたときに見直すこと。
