# usage-tracker

Claude Code の **5時間枠と週次枠の使用率を時系列で記録し、「5時間枠を何回使い切ったら週次リミットに当たるか」を実測で推定する**ツール。

Anthropic はプランごとの枠の内訳を公開していないため、自分の使用履歴から比を求める。

## 何を測るのか

statusline に渡される JSON には、そのときの枠の使用率が入っている。

```
5h 54% (resets 20:54)   7d 97% (resets Sat 09:00)
```

この2つを継続的に記録すると、**5時間枠1本を x% 使ったとき週次枠が y% 進む**という対応が取れる。
5時間枠ごとに (x, y) を集め、原点を通る直線を当てれば

```
5h枠を100%使い切ったときの週次枠の消費 = slope × 100  [%]
週次リミットに当たるまでの満タン回数     = 100 ÷ (slope × 100)
```

が出る。これが `analyze.js` の主結論。

> **注意: いま出る推定値は週次枠が一時的に引き上げられている期間のもの。**
>
> 2026-08-19 まで Claude Code の週間制限が通常の 1.5 倍になっている。`used_percentage` は枠の容量に対する割合なので、この期間は同じ作業量でも週次枠の進みが 1/1.5 に圧縮される。収集を開始した 2026-07-31 以降のデータは全てこの期間のものなので、**平常時の満タン回数は `analyze.js` の出力を 1.5 で割った値**になる(実測 8.24 回 → 平常時は約 5.5 回)。
>
> この補正は `analyze.js` に入れていない。期間判定を持たせると、引き上げが延長・変更・撤回されたときに黙って嘘をつくため。手元で割る方が誤りに気付ける。2026-08-19 を過ぎたデータが溜まれば係数は自然に平常時の値へ収束するので、そのとき推定を取り直す。
>
> なおこの換算は「引き上げ対象が週次枠のみ」という前提に立つ。5時間枠側も引き上げられているなら 5h 満タンの絶対量自体が変わるため、単純に 1.5 で割っても平常時の値にはならない。

## 仕組み

使用率は **statusline の入力 JSON にしか現れない**。transcript(`~/.claude/projects/**/*.jsonl`) にも API レスポンスにも残らないため、後から復元できない。したがって収集は statusline に相乗りする。

```
Claude Code ──(stdin JSON)──> ~/.claude/statusline.js
                                     │ 表示を出したあと
                                     └─> usage-tracker/collect.js
                                              └─> ~/.claude/usage-tracker/usage.jsonl
```

- 追記は**使用率かリセット時刻が動いたとき**か、変化がなくても **10分経過したとき**。statusline は表示更新ごとに何度も呼ばれるため、そのままではログが肥大化する。
- 収集側の失敗は全て飲み込む。statusline が消えると原因の切り分けが不能になるので、取りこぼしよりも表示の安定を優先している。
- 注入は `install.ps1` が**配置済みの** `~/.claude/statusline.js` の末尾に行う。`claude-statusline` 側のソースは変更しない(独立したツールなので依存を焼き込まない)。

## インストール

```powershell
# 収集を開始する
pwsh -File C:\claude\ClaudeCode\usage-tracker\install.ps1

# 入れ直す(statusline.js を再デプロイしたあとなど)
pwsh -File .\install.ps1 -Force

# 外す
pwsh -File .\install.ps1 -Uninstall
```

冪等で、注入後に `node --check` を通す。構文が壊れたらバックアップ(`statusline.js.bak-usage-tracker`)から自動で戻す。

`CLAUDE_STATUSLINE_HOOK` 環境変数を設定すると、そちらのモジュールが優先して読まれる(パスを固定したくない場合用)。

## 分析

```powershell
node analyze.js                      # コンソールサマリ + report.html を生成
node analyze.js --json               # 集計結果を JSON で出す
node analyze.js --log <path> --html <path>
node analyze.js --weeks 2            # 時系列グラフを週次枠の直近2窓ぶんにする(既定は1窓)
node analyze.js --weeks all          # 時系列グラフを全期間にする
node analyze.js --days 1             # 週次枠の窓ではなく日数で絞る
node analyze.js --account team       # 指定したアカウント(acct の値)だけに絞って集計する
node analyze.js --account all        # 全アカウントを混在させたまま集計する(推定値は参考値扱い)
```

複数アカウント(組織 Team + 個人 Pro など)を使い分けている場合、`analyze.js` は**既定でいまログイン中のアカウントだけ**を対象にする(`~/.claude/.credentials.json` の `subscriptionType` で判定)。5時間枠・週次枠はアカウントごとに容量が独立しているため、混在させたまま集計すると window の同一性判定や週次枠の窓分割が壊れる。`--account <名前>` で明示的に切り替えられ、`--account all` を指定したときだけ全アカウントを混在させる(このときは回帰の傾き・満タン回数の推定値が意味を持たない旨の警告をコンソールと HTML の両方に出す)。対象行数が0件になった場合は異常終了せず、アカウントごとの行数内訳を表示する。

なお `acct` の実体はプラン種別なので、**同じアカウントでもプランを変えると別枠に分かれる**(2026-08-10 に個人アカウントを Pro → Max 5x に変更し、`"pro"` → `"max"` へ分岐した)。プランが変われば枠の容量も変わり、過去の実測値をそのまま当てはめられないので、分かれるのはむしろ正しい挙動。畳まずに `--account pro` / `--account max` と別々に見ること。切り替わったことはレポート冒頭の「対象行数 N / 全体行数 M」の差で気づける。`collect-state-<アカウント>.json` も同時に分かれるため、切り替え直後の1窓だけは前プランの窓開始時刻を引き継がない。

HTML レポートには時系列グラフ(5h/7d)、5時間枠ごとの散布図と回帰直線、枠の一覧表が入る。単一ファイルで自己完結している。

時系列グラフだけは既定で**週次枠の直近1窓**に絞る。ログは消さずに増え続けるため、全期間を描くと横軸が伸び続けて波形が潰れるため。日数ではなく週次枠のリセット境界で区切るので、7d% の線は必ずリセット直後から始まり「いまの週次枠をどれだけ使ったか」がそのまま読める。点が密になると実測点のドットだけ等間隔に間引くが、折れ線は全点で描くので波形は失われない。何点・何窓を省いたかはグラフ上部に必ず表示する。

**この絞り込みは表示だけに効く。**コンソールのサマリ・回帰・window 一覧は `--weeks` / `--days` に関係なく常に全期間のデータを使う(グラフの見た目を変えたつもりが推定値まで動く事故を防ぐため)。

## 枠切れ前の引き継ぎ(guard.js)

枠を使い切ると会話は途中で強制的に打ち切られ、何をしていたかの記録が残らない。`guard.js` は使用率が閾値を超えたときに、作業を畳んで `/wrap` で引き継ぎを残すよう Claude に促す。

各枠を**2段構え**で見る。1段目で気付かせ、無視されても2段目で最後にもう一度促す。1段目だけだと、そこで作業を続ける判断をしたセッションは以後まったく警告を受けずに上限へ激突する。

**段によって促す強さが違う。1段目はどちらの枠でも残量を意識させるだけで、作業は畳ませない。畳ませるのは2段目だけ**(次に止まるときは枠切れなので、最短で切り上げて `/wrap` を打ち、そこで終了させる)。1段目でも畳ませていた頃は、リセットまで最大5時間しかない5時間枠のために作業を止めており、中断のコストの割に守れるものが小さかった。

| 枠 | 段 | 既定 | 環境変数 | 促す内容 |
|---|---|---|---|---|
| 5時間枠 | 警告 | 92% | `CLAUDE_USAGE_GUARD_THRESHOLD` | 残量を意識させる。まだ畳ませない |
| 5時間枠 | 最終 | 97% | `CLAUDE_USAGE_GUARD_FINAL_THRESHOLD` | 最短で切り上げて `/wrap`、そこで終了 |
| 週次枠 | 警告 | 90%(team)/ 92%(max・pro) | `CLAUDE_USAGE_GUARD_WEEK_THRESHOLD` | 大きな作業の前に残量を確認。まだ畳ませない |
| 週次枠 | 最終 | 97% | `CLAUDE_USAGE_GUARD_WEEK_FINAL_THRESHOLD` | 最短で切り上げて `/wrap`、そこで終了 |

既定値は**アカウントごとに持つ**(`guard.js` の `DEFAULTS`)。5時間枠1本が週次枠の何%を食うかはプランによって違うため、同じ「残り x%」でも意味が変わる。実測が無いアカウントには、最も容量の小さい team の値を当てて安全側に倒す。上の環境変数にアカウント名(`subscriptionType`)を大文字で付けた `CLAUDE_USAGE_GUARD_WEEK_THRESHOLD_TEAM` のような変数があればそれを優先し、無ければサフィックス無しの共通変数、それも無ければ既定値を使う。実測値は `analyze.js` をアカウント別に走らせれば出る。

2つの枠は**独立に判定・発火**する。リセット周期が違い(5時間枠は数時間で戻るが、週次枠は最大7日戻らない)、切迫の意味も違うため。同時に該当したときは1通にまとめる。既に最終段を超えている状態で開始したセッションでは、警告段を飛ばして最終段だけを出す。

**週次枠に最終段が要る理由** — 5時間枠のガードは週次枠切れを一切防げない。週次が尽きるとき5時間枠は 20% のままでありうるので、5h側は一度も発火しない。この段がないと週次の枠切れは必ず予告なしに来る。

閾値の根拠は実測にある(2026-07-31〜08-19 のログ。数字は `analyze.js` で再計算できる)。

- **5時間枠1本を使い切ったときに進む週次 pt** — team 12.4 / max 9.7 / pro 9.8。週次枠が持つ5時間枠の本数は team 8.0 / max 10.3 / pro 10.2 本。
- **週次枠の警告**は「残量が5時間枠1本前後になったら知らせる」に合わせる。残りちょうど1本の点は team 87.6%、max 90.3%、pro 90.2% だが、既定はその少し先の 90% / 92%(いずれも残り約 0.8 本)に置いた。週次には最終段があって取りこぼしても最後にもう一度促せるため、1段目を厳密に1本へ合わせる利得は小さく、早すぎる警告を毎回無視する習慣がつく方が高くつく。旧既定の一律 85% は Team 時代の値で、どのプランでも残り 15% は5時間枠 1.2〜1.5 本分あり、まだ数時間は普通に作業できる段階で促していた(容量の大きい max ほどこのずれが大きい)。
- **5時間枠の警告**は大きくは上げられない。90% から枠切れまでは実測で中央 11〜12 分・最短 4 分しかなく、「余裕がある段階」ではない。92% でも中央 9 分は残り、`/wrap` 1回(数リクエスト。1リクエストあたり5時間枠を平均 1.5pt 消費)には間に合う。95% を超えると枠切れまで 0 分の例があるため、最終段 97% はこれ以上動かさない。
- **5時間枠の最終段は `/wrap` を保証しない**。97% は残り約 3pt で、`/wrap` 1回の 5〜10pt に届かないことがある。確実に間に合わせるには `/wrap` が収まる警告段(92% = 残り約 8pt)で畳ませるしかないが、それは数時間で戻る枠のために毎回作業を止めることを意味する。中断のコストの方が大きいと判断し、5時間枠の最終段は「間に合えば拾える最後の一手」という位置づけで置いている。週次枠の最終段が同じ 97% でも足りるのは、週次 1pt が5時間枠の 8〜10pt に相当するため。
- **週次枠の最終段 97%** は据え置き。週次1pt は5時間枠の 8〜10pt に相当するので、3% 残っていれば `/wrap` には桁違いに足りる。99% にしないのは、使用率が整数で返るうえ `collect-state-<アカウント>.json` に最大15分の遅れがあるため(週次は実測で30分に最大 7〜10pt 進むので、98% では気付いた時点で尽きていることがある)。

```
PostToolUse ─> guard.js ─> additionalContext で通知(ブロックしない)
Stop        ─> guard.js ─> exit 2 でターン終了を差し止め、stderr で通知
```

- **ブロックしない**。`PreToolUse` で止めると引き継ぎを書くための `worklog` 実行まで巻き添えになり、それを避けるための例外処理が必要になる。`PostToolUse` はツールが実行済みなので止めようがなく、通知だけが残る。区切りの場所は Claude が選ぶ。
- `Stop` を併用するのは、**ツールを使わないターンでは `PostToolUse` が発火しない**ため。その取りこぼしを拾う保険。`stop_hook_active` を見て自分が止めたターンで再発火しないようにしている。
- 発火は**枠あたり・段階あたり・セッションあたり1回だけ**。フラグは枠のリセット時刻をキーに記録するので、枠が変わればひとりでに解除される。
- フラグは `guard-state/<session_id>.json` と**セッションごとに別ファイル**に持つ。Claude Code は同時に何本も動かせるため、1ファイルを共有すると読み書きが衝突するうえ、最初に閾値を踏んだ1本だけが通知を受けて残りが引き継ぎを残せなくなる。終了したセッションのフラグは誰も消さないので、発火のついでに14日より古いものを掃除する。
- 促し文では**コミットさせない**。この時点のコードは検証を通していない。代わりに `git status --short` の結果を引き継ぎに含めさせ、次のセッションが未コミット変更に気付けるようにする。
- 使用率はフックの入力に含まれないため、`collect.js` が最後に書いた `collect-state-<アカウント>.json` を読む。15分より古い値は信用せず何もしない(枠の切り替わり直後の誤発火を避けるため)。

5時間枠の警告 90% も実測に基づく — 90% から 99% まで約20分、持続的な最速消費でも 1.2pt/分だったので、引き継ぎを書く余裕は十分にある。

### 登録

`guard-hooks-snippet.json` の内容を `~/.claude/settings.json` の `hooks` にマージする。`install.ps1` は statusline.js への注入専用で、settings.json には触らない(共有ファイルを機械的に書き換えると整形が壊れやすいため)。

スニペット中の `guard.js` のパスは**このリポジトリを `C:/claude/ClaudeCode` に置いた場合の絶対パス**なので、別の場所に配置したなら書き換える。フックは任意のディレクトリから起動されるため相対パスにはできない。

```powershell
node guard.js status [session_id]   # 使用率・全セッションのフラグ・発火判定を表示する
node guard.js reset                 # 全セッションの発火済みフラグを消す(動作確認用)
```

## データ形式

`~/.claude/usage-tracker/usage.jsonl` に1行1レコード。

| フィールド | 内容 |
| --- | --- |
| `ts` | 記録時刻 (ISO 8601, UTC) |
| `acct` | 記録時にログインしていたアカウント(`subscriptionType`。`"team"` / `"pro"` など、判別不能なら `"unknown"`)。マイグレーション前の既存行には無く、`analyze.js` はその場合 `"unknown"` として扱う |
| `five_pct` / `seven_pct` | 5時間枠 / 週次枠の使用率 (0-100) |
| `five_reset` / `seven_reset` | リセット時刻。**Unix epoch 秒**で来る(ISO 文字列も許容) |
| `model` / `effort` / `fast` | そのときのモデル・推論強度・fast モード |
| `in_tok` / `out_tok` | コンテキスト窓の累積入出力トークン |
| `cost` | セッションの `total_cost_usd` |
| `sid` | セッション ID |

**同じ `five_reset` を持つ行の集まりが1つの5時間枠**。枠の識別はこの値で行う(使用率の下落ではなく)。

差分判定に使う「最後に書いた行」は `collect-state-<アカウント>.json` としてアカウント別に持つ。
共有すると `/login` のたびに使用率が飛んだと誤認して、間引きが効かなくなるため。

### 既存ログへのアカウント付与(1回だけ)

`acct` を記録するようになる前の行にはこのフィールドが無い。`analyze.js` は既定で現在の
アカウントに絞って集計するため、放置すると過去のデータが丸ごと集計から外れる。

```console
$ node migrate-account.js --acct team --dry-run   # 何行が対象か確認する
$ node migrate-account.js --acct team             # 付与する(バックアップを残す)
```

付ける値に既定値は無く、必ず `--acct` で指定させる。「`acct` が無い＝当時の唯一のアカウント」が
何だったかは実行する本人にしか判断できず、取り違えたまま実行すると別アカウントの枠のデータと
して混ざって回帰の傾きが静かに狂うため。既に `acct` を持つ行は変更しないので、何度実行しても
結果は変わらない。

## transcript ベースの分析ツール(transcript/)

`analyze.js` が読む `usage.jsonl` とはデータソースが別系統。`transcript/` 配下のスクリプトは Claude Code 本体が書く会話 transcript (`~/.claude/projects/**/*.jsonl`) を直接読む。統計取り違え防止のため、どちらの入力を見ているかは常に意識すること。

- `transcript/sessions.js` — セッションごとのコスト・到達コンテキスト長・委譲回数(重いツール直接呼び出し vs サブエージェント委譲)を集計し、コスト上位セッションの表を出す。
- `transcript/turncost.js` — Opus 系メインスレッドのみ抽出し、コンテキスト長バケット別の「1ターンあたり単価」と 30〜60K 帯を 1.0 とした倍率を出す。
- `transcript/breakdown.js` — モデル×レイヤー(main/subagent)別のトークン内訳と、tool_result の総文字数をツール別に出す。「どのツールの出力が文脈を太らせているか」= 委譲候補を見つけるのが目的。

```powershell
node transcript/sessions.js
node transcript/turncost.js
node transcript/breakdown.js
node test/run.js               # test/*.test.js を一括実行(偽 HOME を使うので実データは読まない)
node test/run.js guard         # 名前の一部で絞って実行
node test/transcript.test.js   # 1 ファイルだけ実行したいとき
```

`test/run.js` は起動時に `test/.tmp/` を丸ごと消して、前回実行の孤児(ハングしたまま残ったプロセスが握っていたファイル)を一掃する。ただし名前で絞った実行では全削除をスキップする(別スイートを並列に流しているとき、そのサンドボックスを巻き添えで消さないため)。掃除したいときは引数なしで全実行すること。

共通処理は `transcript/lib.js`(走査・コスト換算・コンテキスト長)、モデル別単価テーブルは `transcript/pricing.js` にある。単価表に無いモデルは $0 として集計した上で、実行の最後に名前と件数を警告する(新モデルが黙って集計から漏れるのを防ぐため)。

### コンテキスト長は3つの内訳の和で数える

`cache_read_input_tokens` だけを「そのターンのコンテキスト長」として使ってはいけない。キャッシュの TTL が切れた直後のターンは同じ量が `cache_creation_input_tokens` 側に乗るため、実際は 200K のターンが「ほぼ 0」に見える。`input` / `cache_creation` / `cache_read` は互いに排他な内訳なので、**3つの和が総プロンプト長**になる(`lib.js` の `ctxLen`)。

この誤りは倍率を過小評価させる。cache_read だけで分類していたときは最小の帯(〜30K)に 408 ターンが落ちて単価が基準の 2.8 倍に見えていたが、和で数えるとこの帯は**ターン数 0** になる。システムプロンプト・ツール定義・CLAUDE.md だけでプロンプト長の下限が 30K を超えるので、そこに入るターンは原理的に存在しない。倍率の基準を 30〜60K に置いているのはこのため(〜30K 帯にターンが現れたら算入漏れを疑う)。

## 限界

読み方を誤らないために、分かっている制約を挙げる。

- **使用率の分解能は1%**。API が整数で返すため、1つの5時間枠での週次枠の増分が数%だと丸め誤差の影響が大きい。複数の枠を回帰にかけて緩和する前提。有効な枠が2本未満のとき、および全ての枠で 7d 増分が0に丸まって傾きが正にならないときは、`analyze.js` は推定を出さず「推定不可」と表示する(無意味な数字を出すよりデータ待ちであることを示す)。
- **`claude -p` では statusline が呼ばれない**。`claude-window-keeper` の定期 ping は非対話実行なので点が増えない。使っていない間は枠も進まないので分析上の実害はないが、「枠が切り替わった瞬間」は記録されず、次に対話を開いたときに初めて分かる。
- **週次枠が既に高い週からは何も測れない**。残り3%の状態で観測できるのは3%分の増分だけ。週次リセット後の1週間が本番のデータになる。観測できた週次リセットは土 09:00 JST(`1785542400` = 2026-08-01 00:00 UTC)。これが固定曜日なのか使用開始からの7日ローリングなのかは、次のリセット時刻を見れば分かる(`analyze.js` は `seven_reset` の変化を枠の切り替わりとして記録する)。
- **モデルと推論強度で消費レートが変わる**。Opus と Haiku が混在した枠は傾きが揺れる。枠ごとのモデル内訳を見て、傾向が違う枠は分けて解釈する。
- `in_tok` / `out_tok` は**コンテキスト窓の累積でセッション単位**。プランの枠に計上される総消費量ではないので、「%あたり何トークン」の目安にはなるが絶対値としては使えない。
- **Anthropic 側が枠の定義や重み付けを変えると過去データと比較できない**。時系列を残しているのはそのため(傾きが途中で変わったら定義変更を疑う)。
- 5時間枠と週次枠が**同じ消費を同じ重みで数えている保証はない**。このツールが測るのはあくまで両者の観測上の比。
- **`transcript/` 配下の分析はアカウントを区別できない**。`usage.jsonl` と違い、transcript は Claude Code が書くファイルで、レコードにアカウントを示す情報が無い(`userType` はアカウント同定に使えない)。複数アカウントを使い分けている場合、`sessions.js` / `turncost.js` / `breakdown.js` の集計は**両方を黙って合算する**。分けたいときは対象ディレクトリか期間で絞るしかない。なお `pricing.js` は API 定価での換算なのでプラン種別には依存しない——裏を返すと、この換算コストは**どちらのアカウントの枠を消費したかを一切表さない**。
