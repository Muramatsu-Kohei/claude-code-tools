# account-guard

特定のディレクトリツリーを、許可したアカウント以外から触れないようにする Claude Code フック。

複数の Claude アカウント(組織の Team と個人の Pro など)を1台のマシンで使い分けるとき、
**組織のコードを個人アカウントで読ませてしまう事故**を防ぐためのもの。

## なぜ必要か

Claude Code の認証情報 `~/.claude/.credentials.json` はマシンに1つしかなく、`/login` は
マシン全体に即座に効く。一方で作業ディレクトリはアカウントと無関係に到達できる
(`C:\claude` で作業していても Read も Bash も `C:\org-tree\...` を読める)。
つまり **ディレクトリの使い分けは規約であって技術的な壁ではない**。

このフックは「このツリーはこのアカウント専用」という対応を実際に強制する。

## 仕組みと制約

判定材料は `.credentials.json` の `claudeAiOauth.subscriptionType`(`"team"` / `"pro"` / `"max"`)。
credentials に uuid やメールアドレスのような identity フィールドは存在しないため、
**プラン種別で代用している**。したがって次の制約がある。

- 判別できるのは「どのプランか」であって「どのアカウントか」ではない。
  **同じプランのアカウントを2つ持つと区別できない**(Team 1つ + 個人 Pro 1つなら成立する)。
- `subscriptionType` は文書化された API ではない。Claude Code の更新で構造が変わりうる。
  読めない場合は判別不能として**拒否側に倒す**(素通しになって気づかないより、止まって気づけるほうがよい)。
- **プランを変更すると識別子そのものが変わる**。同じアカウントでも Pro から Max に変えれば
  `"pro"` → `"max"` になる(2026-08-10 に実際に発生)。`allow` に**守りたい側のプランだけを
  列挙する**なら影響しないが、締め出したい側を名指しする書き方(拒否リスト的な使い方)をしていると、
  プラン変更で条件から外れて**保護が静かに外れる**。`allow: ["team"]` のような許可リストで書くこと。
  なお `subscriptionType` は Max 5x と 20x を区別しない(どちらも `"max"`)。倍率まで見たい場合は
  同じファイルの `rateLimitTier`(例 `"default_claude_max_5x"`)を使う。

### ブロックは PreToolUse でしか行えない

当初は `SessionStart` で `continue: false` を返してセッション開始ごと止める設計を検討したが、
公式ドキュメントで `SessionStart` は "Context only / No blocking or decision control" と
明記されており、`continue: false` も exit code 2 もセッションを止められない。
実際にブロックできるのは `PreToolUse` の `permissionDecision: "deny"` だけなので、防御はそこに置いている。
`SessionStart` と `CwdChanged` には**警告を出す役割だけ**を持たせている。

### 何を見て判定するか

1. **作業ディレクトリ**(`cwd`)が保護ツリーの内側にあるか。内側なら全ツールを拒否する。
2. **ツールの操作対象**が保護ツリーを指すか。見るフィールドはツールによって違う。
   - `Read` / `Edit` / `Write` / `NotebookEdit` — パス引数(`file_path` など)だけ
   - `Glob` — `path`(検索起点)と `pattern`(glob 式)。`pattern` 単体でも保護ツリーを
     列挙できるため両方見る。
   - `Grep` — `path` と、パスフィルタの `glob`。**検索語の `pattern` は見ない**。
     これは正規表現であってパスではなく、含めると保護ツリー名を検索語に含めただけで
     拒否される誤検知が起きる。
   - `Bash` / `PowerShell` — コマンド文字列の全体
   - `Agent` / `Task` — 指示文の全体(サブエージェントに読ませる指示そのものを止めるため)
   - 上記以外の未知のツール(MCP のファイルシステム系ツールなど) — 引数からパス形式に
     見える部分文字列だけを拾う(引数全体の文字列比較だと散文中のツリー名にも反応するため)

`Edit` の編集内容や `Write` の書き込み内容は**見ない**。ここを見ると、保護ツリーについて
書いたドキュメントを別の場所で編集しようとしただけで拒否される。保護ツリーのファイルに
触れていない操作を止めても守るものは増えず、日常の邪魔になる分ガードを外したくなるだけ。

### 検出できないケース

- ツリー名だけの言及(`org-tree` という文字列)は**検出しない**。ドキュメントや会話で名前に
  触れただけで拒否されると誤検知の実害のほうが大きいため、パスの形での一致のみを見ている。
- **シンボリックリンク / ジャンクション経由の到達**は追わない。判定はパス文字列を
  正規化して突き合わせるだけで、リンクの解決はしていない。
- **UNC パス**(`\\?\C:\...`、`\\localhost\c$\...`)や 8.3 短縮名は未対応。

判定前にパスを解決するため、相対パス(`../org-tree/x.py`)、途中で上に登る絶対パス
(`C:/x/../org-tree/x.py`)、Git Bash 形式(`/c/org-tree/x.py`、`/cygdrive/c/...`)は
いずれも**拒否される**(いずれも回帰テストで確認している)。

このガードが想定している相手は自分自身であり、悪意ある回避を防ぐものではない。事故を防ぐためのもの。

### 保護ツリーのパスは例示でも止まる

`Agent` / `Task` の指示文は全体を見るため、**サブエージェントへの指示の中で保護ツリーを
例として挙げただけでも拒否される**。実際に、このツールの改修をサブエージェントへ委譲する際、
指示文に「保護対象のツリー(例: `C:/org-tree`)」と書いたところで止まった。

これは仕様どおりで、直さない。ガードから見れば「例として書いたパス」と「実際に読ませる
指示」は区別できず、区別できない以上は止めるのが正しい。サブエージェントに保護ツリーの
話をするときは、`C:/org-tree` のような架空のパスを使うこと。

### ガード自身が異常終了したとき

判定できる範囲 —— 作業ディレクトリが保護ツリーの内側かどうか —— だけを見て、内側なら拒否、
外側なら通す。拒否メッセージには復旧手順(`git checkout`)を含める。

以前は無条件に拒否していたが、それだとガードが壊れた瞬間にマシン上の**全ツール呼び出し**が
止まる。実際にこれが起きたとき、ガードを直す `Edit` も壊れたファイルを読む `Read` も通らず、
Claude Code の外から git で戻すしか手がなくなった。保護ツリーと無関係な作業まで巻き添えに
するのは「判定できたものだけを拒否する」方針にも反するため、cwd 判定に絞っている。

自分自身をフックとして動かすツールなので、**改修は 1 回の書き込みで完結させること。**
シグネチャの変更と呼び出し元の修正を別々の編集に分けると、1 つ目で壊れた時点で 2 つ目が
通らなくなる。テストは `test/` を直接実行するのでフックを経由しない。

## 設定

保護するツリーは**設定ファイルで明示する**。既定では何も保護しない
(実在するパスをリポジトリに焼き込まないため)。

`~/.claude/account-guard/config.json` を作る:

```json
{
  "rules": [
    { "tree": "C:/org-tree", "allow": ["team"] }
  ]
}
```

- `tree` — そのアカウント専用にしたいディレクトリ。区切りは `/` でも `\` でもよい。
- `allow` — 触れてよいアカウント(`subscriptionType` の値)。ここに無いアカウントでは拒否される。

`config.example.json` がひな形。

## インストール

1. 上記の `config.json` を作る。
2. `hooks-snippet.json` の内容を `~/.claude/settings.json` の `hooks` にマージする。
   既に同じイベントの配列があるときは、置き換えずに要素として追加すること。
   **`command` の `node C:/claude/ClaudeCode/account-guard/account-guard.js` は作者の環境の
   パスなので、自分が `account-guard.js` を置いた場所に書き換えること。** パスを直し忘れると
   フックのプロセスが起動に失敗し、deny が一切出ないまま(= fail-open)保護が無効になる。
   しかもエラーが目に見える形では出ないので、`status` サブコマンドや下記の確認手順で
   実際に拒否されることを必ず確かめること。
   **`account-guard.js` を移すときは、同じディレクトリに `credentials.js` も一緒に置くこと。**
   ガードはこれを読んでアカウントを判別する。無いと判別不能として保護ツリーへの操作を
   すべて拒否するので、素通しにはならないが、許可されたアカウントで入っていても止まる。
3. 設定できたか確認する:

```console
$ node account-guard.js status
アカウント: pro
設定: C:\Users\<user>\.claude\account-guard\config.json
  C:/org-tree  allow=[team]  → 現在は 拒否
```

特定のディレクトリで拒否されるかを試すこともできる:

```console
$ node account-guard.js status C:/org-tree/some-project
判定(cwd=C:/org-tree/some-project): 拒否 — 作業ディレクトリが C:/org-tree 配下にあります
```

## 拒否されたときの挙動

ツール呼び出しがブロックされ、理由が Claude とユーザーの双方に表示される。
許可されたアカウントに切り替えれば通るようになるが、順序を守ること。拒否の文面も同じ順序で
案内する: **先に `swap save` で現在のアカウントを退避してから** `swap <name>` で切り替える。
いきなり `/login` すると、まだ退避していないアカウントの認証情報はその時点で消える(後述の
`swap.js` を参照)。

保護ルールを設定していない状態では、このフックは**何も拒否しない**。
`status` で「保護ルール: なし」と出ていないか確認すること。

## アカウントを切り替える (`swap.js`)

ガードは「今のアカウントでは触るな」としか言わない。実際に切り替える側が `swap.js`。

`/login` はブラウザ OAuth を毎回踏む必要があるが、切り替えで実際に変わるのは
`~/.claude/.credentials.json` の 1 本だけで、CLAUDE.md・memory・skills・履歴は共有された
ままになる。それならファイルを退避して入れ替えるほうが速い、という判断
(比較検討は `docs/account-separation.md` §6.1)。

```console
$ swap                  # 現在のアカウントと退避済み一覧
現在のアカウント: pro  [pro から復元]
  C:\Users\<user>\.claude\.credentials.json  [残り 26 日]

退避済み (C:\Users\<user>\.claude\accounts):
* pro       [残り 26 日]
  team      [残り 12 日]

$ swap team             # 現在(pro)を退避してから team を復元
退避: pro
切り替え: pro -> team  [残り 12 日]

$ swap save             # 切り替えずに退避するだけ
```

退避先は `~/.claude/accounts/<name>.json`。元の credentials と同じ ACL を継承させるため
`~/.claude` の下に置いている。平文トークンの本数は増えるが保護レベルは変わらない。
同じディレクトリの `.current` に「現在のログインがどのスロット由来か」を記録している
(一覧の `*` 印はこれ)。消しても壊れないが、消すと次の退避先を名前から推測することになる。
既存の退避を上書きするときは、旧内容の控えを `accounts/.replaced/<name>-N.json` に残す
(スロットごとに 2 本まで。ただし落とすのは「失効済み」「同じ資格情報が他にも残っている」
「読めない」と言えるものだけで、どれでもない控えは上限を超えても残す)。取り違えて上書きしても
`accounts/<name>.json` へ戻せば復旧できる。同じディレクトリの `.unreadable-current-N.json` は
「読めなかった現在の credentials」の控えで、復元には使えない(スロットへ戻さないこと)。
`swap` の status は両者を別の項目として表示する。

`swap.cmd` は cmd / PowerShell から短く叩くためのラッパー。中の `swap.js` へのパスは
作者の環境のものなので、**自分の置き場所に書き換えてから** PATH の通った場所に置くこと。
`swap.js` を別の場所へ移すときは `credentials.js` も同じディレクトリへ置くこと
(アカウントの読み方をガードと共有している)。置き忘れた場合は理由を示して止まる。

### 使う前に知っておくこと

- **一度も `save` していないアカウントには切り替えられない。** 初回は
  「いま入っているアカウントを `swap save` → `/login` でもう一方に入る → そちらも
  `swap save <名前>`」の順で通すこと。**先に `/login` してはいけない。** Claude Code が
  `.credentials.json` を置き換えるので、まだ退避していないアカウントの認証情報は
  その時点で消え、復旧にはブラウザ OAuth のやり直しが要る。
  2 回目の退避で**名前を明示する**のは、`/login` を挟むと来歴が前のアカウントを指したまま
  古くなるため。省略すると前のスロットを上書きしようとする(プラン種別が違えば別アカウントだと
  分かるので中止するが、同じプラン同士では判別できない)。
- **切り替えはマシン全体に即座に効く。** 稼働中の別セッションも次のリクエストから新しい
  アカウントになる。だからタイマーやフックから自動実行してはならない(`docs/account-separation.md` §1.3)。
- **アカウントの同一性は「証明できたこと」だけで判断する。** credentials に uuid や
  メールアドレスのような identity フィールドが無いので、中身から「誰のログインか」は分からない。
  使える材料は 3 つで、証明できる範囲が違う。
  (1) `refreshToken` の一致 = 同じ資格情報である証明、
  (2) `subscriptionType` の**不一致** = 同じアカウントの同じ世代ではないことの証明。
  別アカウントである証明にはならない(同じアカウントが Pro → Max と変わると、変更前に退避した
  スロットとは種別が食い違う)。一致のほうは何も証明しない。一致を同一と読むと、同一プランの
  別アカウントを取り違えて相手の唯一のバックアップを消す、
  (3) `.current`(来歴)= 前回このツールが書いた先の記録で、外から `/login` されたり
  書き込みが途中で落ちたりすると古くなるので、単独では上書きの根拠にしない。
  1 回の退避で書き込むのは、**名前で指定された 1 スロットだけ**。1 つのアカウントを 2 つの名前で
  退避していると片方が古いまま取り残されるが、そこを揃えて書き換えるには「旧内容と現在のログインが
  同じアカウント」だと言える必要があり、(1) の証明が無い限りそれは言えない。(3) を根拠にすると、
  同一プランの別アカウントを取り違えて、名前を挙げてもいないスロットまで巻き添えに潰す。
  取り残されうるスロットは書き換えず、退避のたびに名前を挙げて知らせる。ただし「古い」とは
  断定しない。現在のログインが同じアカウントの新しい世代なのか、別アカウントへ `/login` した
  結果なのかは見分けられず、後者に更新を勧めると相手の唯一のバックアップを潰すため
  (初回手順の 2 回目の退避がまさにこれに当たる)。同じアカウントの更新だと分かっているときだけ
  `swap save <name> --force`。この信号は `swap` の一覧にも `[現在のログインと内容が違います]`
  として残るので、退避したときの表示を見逃しても後から気づける。
  退避名の既定値(名前を省略したとき)は、来歴が無ければ `subscriptionType` から作る。
  スロット名にサブコマンドと同じ語(`save` / `help` など)は使えない。作れてしまうと
  `swap <name>` がサブコマンドとして解釈され、そのスロットを復元する手段が無くなるため。
- **既存スロットを別の認証情報で上書きしようとすると中止する。** `swap save team` の打ち間違いなどで、
  そのアカウントの唯一のバックアップが消えるのを防ぐため。同じアカウントだと分かっているなら
  `swap save <name> --force`。同一プラン同士は原理的に判別できないので、そこは判断ではなく構造で守る。
  上書きの前に旧内容を `accounts/.replaced/` へ控えるので、取り違えても改名で戻せる
  （控えはスロットごとに 2 本までだが、他に複製が残っていると言えない控えは上限を超えても残す。
  本数のために唯一の 1 本を消しては本末転倒なので）。
- **切り替えが起きなかったときは終了コードを成功にしない。** 「すでにそのスロットから復元した
  状態」で認証を変えなかった場合など、要求された切り替えが起きていない経路は非ゼロで終わる。
  `swap team && claude -p ...` のようなラッパーが、別のアカウントのまま次の処理へ進まないため。
- **`--force` の意味は退避側と復元側で別。** `swap <name> --force` は復元側の判断
  （失効済み・`subscriptionType` 無し・同一プランでも復元する、現在の credentials が読めなくても
  控えを残して進む）で、**退避先に別のアカウントが入っていれば、それでも中止する**。
  スロットを上書きしてよいという明示は `swap save <name> --force` だけ。1 つの旗にまとめると、
  復元の都合で付けた `--force` が、退避名（プラン種別由来のことがある）に当たった無関係の
  スロットを黙って潰す。
- **復元先が「別アカウント」だと証明できないときは切り替えを中止する。** 同一プラン（または
  プラン種別を読めない）の相手は、別アカウントなのか自分の古い退避なのか判別できない。後者だと
  ローテート前のトークンに戻り、稼働中のセッションが次のリクエストで認証エラーになる。
  来歴の有無では判断を変えない（来歴が語るのは現在のログインの出どころだけで、復元先が何者かは
  何も証明しない）。別アカウントだと分かっているなら `swap <name> --force`。
- **`refreshToken` には有効期限がある。** 失効済みのものを復元しても `/login` のやり直しに
  なるだけなので、切り替えは**実行前に中止する**。失効が近いものは一覧の残り日数で分かる。
  `refreshToken` を持たない中身(手で編集した退避、将来の構造変更)も同じ扱いで中止する。
  復元しても認証を更新できず、`accessToken` が切れた数時間後にマシン全体が認証エラーになるため
  (一覧では `[refreshToken がありません]` と出る)。
- **`subscriptionType` を持たない中身は復元しない。** 復元するとガードが誰のログインか判別できず、
  保護ツリーへの操作がすべて拒否される。元に戻す操作まで巻き添えになるので手前で止める。
- 復元先のファイルは書き換える前に検証する。壊れたファイルで現在のログインを潰すことはない。
  現在の credentials が読めないとき(破損している、他のプロセスが書き込み中、権限が無い)も、
  退避できない以上は切り替えを中止する。**ただし中止したまま抜け出せなくなっては安全ではないので、
  `--force` を付ければ切り替えられる**。読めない中身はスロットには入れず(復元に使えないうえ、
  そこにある有効な退避を潰してしまう)、`accounts/.replaced/` に控えとしてだけ残す。
- **切り替えた直後の使用量ログは 1 行だけ混ざりうる。** `usage-tracker/collect.js` は同じ
  `.credentials.json` でアカウントを判定するため、切り替え後の最初の描画は「新しいアカウント名 +
  切り替え前のレスポンス由来の残量」になる。枠の集計を厳密に見るときは切り替え時刻の前後を
  疑うこと(collect 側での対処は未着手)。
