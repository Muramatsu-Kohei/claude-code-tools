# account-guard

特定のディレクトリツリーを、許可したアカウント以外から触れないようにする Claude Code フック。

複数の Claude アカウント(組織の Team と個人の Pro など)を1台のマシンで使い分けるとき、
**組織のコードを個人アカウントで読ませてしまう事故**を防ぐためのもの。

## なぜ必要か

Claude Code の認証情報 `~/.claude/.credentials.json` はマシンに1つしかなく、`/login` は
マシン全体に即座に効く。一方で作業ディレクトリはアカウントと無関係に到達できる
(`C:\claude` で作業していても Read も Bash も `C:\org-tree\...` を読める)。
つまり **ディレクトリの使い分けは規約であって技術的な壁ではない**。

このフックは「このツリーはこのアカウント専用」という対応を実際に強制する。

## 仕組みと制約

判定材料は `.credentials.json` の `claudeAiOauth.subscriptionType`(`"team"` / `"pro"` / `"max"`)。
credentials に uuid やメールアドレスのような identity フィールドは存在しないため、
**プラン種別で代用している**。したがって次の制約がある。

- 判別できるのは「どのプランか」であって「どのアカウントか」ではない。
  **同じプランのアカウントを2つ持つと区別できない**(Team 1つ + 個人 Pro 1つなら成立する)。
- `subscriptionType` は文書化された API ではない。Claude Code の更新で構造が変わりうる。
  読めない場合は判別不能として**拒否側に倒す**(素通しになって気づかないより、止まって気づけるほうがよい)。
- **プランを変更すると識別子そのものが変わる**。同じアカウントでも Pro から Max に変えれば
  `"pro"` → `"max"` になる(2026-08-10 に実際に発生)。`allow` に**守りたい側のプランだけを
  列挙する**なら影響しないが、締め出したい側を名指しする書き方(拒否リスト的な使い方)をしていると、
  プラン変更で条件から外れて**保護が静かに外れる**。`allow: ["team"]` のような許可リストで書くこと。
  なお `subscriptionType` は Max 5x と 20x を区別しない(どちらも `"max"`)。倍率まで見たい場合は
  同じファイルの `rateLimitTier`(例 `"default_claude_max_5x"`)を使う。

### ブロックは PreToolUse でしか行えない

当初は `SessionStart` で `continue: false` を返してセッション開始ごと止める設計を検討したが、
公式ドキュメントで `SessionStart` は "Context only / No blocking or decision control" と
明記されており、`continue: false` も exit code 2 もセッションを止められない。
実際にブロックできるのは `PreToolUse` の `permissionDecision: "deny"` だけなので、防御はそこに置いている。
`SessionStart` と `CwdChanged` には**警告を出す役割だけ**を持たせている。

### 何を見て判定するか

1. **作業ディレクトリ**(`cwd`)が保護ツリーの内側にあるか。内側なら全ツールを拒否する。
2. **ツールの操作対象**が保護ツリーを指すか。見るフィールドはツールによって違う。
   - `Read` / `Edit` / `Write` / `NotebookEdit` — パス引数(`file_path` など)だけ
   - `Glob` — `path`(検索起点)と `pattern`(glob 式)。`pattern` 単体でも保護ツリーを
     列挙できるため両方見る。
   - `Grep` — `path` と、パスフィルタの `glob`。**検索語の `pattern` は見ない**。
     これは正規表現であってパスではなく、含めると保護ツリー名を検索語に含めただけで
     拒否される誤検知が起きる。
   - `Bash` / `PowerShell` — コマンド文字列の全体
   - `Agent` / `Task` — 指示文の全体(サブエージェントに読ませる指示そのものを止めるため)
   - 上記以外の未知のツール(MCP のファイルシステム系ツールなど) — 引数からパス形式に
     見える部分文字列だけを拾う(引数全体の文字列比較だと散文中のツリー名にも反応するため)

`Edit` の編集内容や `Write` の書き込み内容は**見ない**。ここを見ると、保護ツリーについて
書いたドキュメントを別の場所で編集しようとしただけで拒否される。保護ツリーのファイルに
触れていない操作を止めても守るものは増えず、日常の邪魔になる分ガードを外したくなるだけ。

### 検出できないケース

- ツリー名だけの言及(`org-tree` という文字列)は**検出しない**。ドキュメントや会話で名前に
  触れただけで拒否されると誤検知の実害のほうが大きいため、パスの形での一致のみを見ている。
- **シンボリックリンク / ジャンクション経由の到達**は追わない。判定はパス文字列を
  正規化して突き合わせるだけで、リンクの解決はしていない。
- **UNC パス**(`\\?\C:\...`、`\\localhost\c$\...`)や 8.3 短縮名は未対応。
- **`cd` 以外の方法での移動**は追わない。相対パスの基準に積むのは `cd` / `pushd` /
  `Set-Location` などの移動コマンドだけで、`env -C <dir> <cmd>` や `--cwd` / `--prefix` の
  ように「オプションで移動先を指定する」形は見ていない。一時解除中にこの形で解除範囲の外へ
  出ると、基準が古いまま解決されるため範囲内と判定されうる(解除しておらず、cwd もツリーの
  外にいるときは、そもそも判定が拒否側なので影響しない)。移動コマンドを列挙している以上、
  列挙から漏れたものは残る。
- **一時解除中でも、次の 2 つは拒否側に倒れる**(いずれも過剰拒否で、保護が緩む向きではない)。
  - **解除した範囲の中でのブレース展開**。`cat <解除した場所>/{x,y}` は、展開する前のトークンが
    `{` で切り詰められた扱いになり、範囲内である根拠が得られないため拒否される。展開しきれて
    いても変わらない。切り詰めの印は「兄弟ディレクトリに届く書き方」を止めるためのもので、
    そこを緩めると保護の側が薄くなるため、使い勝手より拒否を選んでいる。
  - **ツリーのルートを経由する多段 `cd`**。`cd <ツリー>/<解除した場所> && …` は通るが、
    `cd <ツリー> && cd <解除した場所> && …` は拒否される。途中の `cd` の移動先(ツリーの
    ルート)がそれ自体で操作対象になり、配下だけの解除では覆えないため。

判定前にパスを解決するため、相対パス(`../org-tree/x.py`)、途中で上に登る絶対パス
(`C:/x/../org-tree/x.py`)、Git Bash 形式(`/c/org-tree/x.py`、`/cygdrive/c/...`)は
いずれも**拒否される**(いずれも回帰テストで確認している)。

このガードが想定している相手は自分自身であり、悪意ある回避を防ぐものではない。事故を防ぐためのもの。

### 保護ツリーのパスは例示でも止まる

`Agent` / `Task` の指示文は全体を見るため、**サブエージェントへの指示の中で保護ツリーを
例として挙げただけでも拒否される**。実際に、このツールの改修をサブエージェントへ委譲する際、
指示文に「保護対象のツリー(例: `C:/org-tree`)」と書いたところで止まった。

これは仕様どおりで、直さない。ガードから見れば「例として書いたパス」と「実際に読ませる
指示」は区別できず、区別できない以上は止めるのが正しい。サブエージェントに保護ツリーの
話をするときは、`C:/org-tree` のような架空のパスを使うこと。

### ガード自身が異常終了したとき

判定できる範囲 —— 作業ディレクトリが保護ツリーの内側かどうか —— だけを見て、内側なら拒否、
外側なら通す。拒否メッセージには復旧手順(`git checkout`)を含める。

以前は無条件に拒否していたが、それだとガードが壊れた瞬間にマシン上の**全ツール呼び出し**が
止まる。実際にこれが起きたとき、ガードを直す `Edit` も壊れたファイルを読む `Read` も通らず、
Claude Code の外から git で戻すしか手がなくなった。保護ツリーと無関係な作業まで巻き添えに
するのは「判定できたものだけを拒否する」方針にも反するため、cwd 判定に絞っている。

自分自身をフックとして動かすツールなので、**改修は 1 回の書き込みで完結させること。**
シグネチャの変更と呼び出し元の修正を別々の編集に分けると、1 つ目で壊れた時点で 2 つ目が
通らなくなる。テストは `test/` を直接実行するのでフックを経由しない。

### テスト

`node test/run.js` で一括実行する(実行前に `test/.tmp/` を丸ごと消すので、前回実行の残骸を
気にしなくてよい。作り直しは各テストが自分のサブディレクトリを掘るときに起きる)。`node test/run.js swap` のように引数を渡すとファイル名の
一部で絞り込める。1 本だけ実行したいときは従来どおり `node test/<名前>.test.js` でもよい。
ただしフィルタや `SWAP_SCRIPT` を指定した実行では `.tmp` の全削除をスキップする(他スイートや
変異版を巻き添えにしないため)。掃除したいときは引数なしで全実行すること。

テストは性質が 2 つに分かれる。

- `swap` / `account-guard` / `probe` … 経路ごとの example test
- `fault` / `reachable` … property test。前者はランダムな操作列に故障(EPERM 等の例外・
  書き込み途中での強制終了・切り詰め)を注入して「実行前の refreshToken が実行後も
  どこかに残っている」を、後者は出力に現れた案内を実際に打って「案内どおり打つと止まらない」を
  検査する。故障は `NODE_OPTIONS=--require test/fault-fs.js` のプリロードで注入するので、
  本番コードにテスト専用のフックは要らない

property test は**変異版で落ちることを確かめてから信用すること。** `SWAP_SCRIPT` に
swap.js のコピーのパスを渡せば対象を差し替えられるので、案内の `--force` を落とす・控えを
取る呼び出しを外すなどの変異を入れて、FAIL が出るかを見る。実際 `reachable.test.js` は
初版が 299 PASS の緑だったが、変異を入れても緑のままで何も検査できていなかった。

コピーを置くディレクトリには `credentials.js` と `subcommands.js` も一緒に置くこと。`swap.js` は
どちらも `require` で隣を読むので、`swap.js` だけを置くと起動直後に落ちて全ケースで
選択肢が 0 件になり、それでも `reachable` は緑のままになる(実測 672 PASS → 520 PASS、FAIL は 0)。
変異の効きは PASS 件数ではなく、集計行の「選択肢が1件以上抽出できたケース」で確かめる。

## 設定

保護するツリーは**設定ファイルで明示する**。既定では何も保護しない
(実在するパスをリポジトリに焼き込まないため)。

`~/.claude/account-guard/config.json` を作る:

```json
{
  "rules": [
    { "tree": "C:/org-tree", "allow": ["team"] }
  ]
}
```

- `tree` — そのアカウント専用にしたいディレクトリ。区切りは `/` でも `\` でもよいが、
  **ドライブ文字から書くこと。** 判定はフックを呼んだ場所を基準にパスを解決するので、
  そうしないと同じ設定でも作業ディレクトリによって守る対象が変わってしまう。
  書き損じ方によって現れ方が違うので、両方を知っておくとよい。
  - **相対パス**(`org-tree`)は書き損じとして弾かれ、設定を直すまで操作を拒否する。
    ただし設定ファイル自身の読み書きだけは通るので、そこから復旧できる
  - **ドライブ文字だけ落とした**(`/org-tree`)は書き損じにならない。どのドライブでも、
    パスの途中に現れても一致する広いルールになり、意図しないディレクトリまで拒否する。
    拒否側に倒れるので保護は外れないが、気づきにくい
- `allow` — 触れてよいアカウント(`subscriptionType` の値)。ここに無いアカウントでは拒否される。

`config.example.json` がひな形。

## インストール

1. 上記の `config.json` を作る。
2. `hooks-snippet.json` の内容を `~/.claude/settings.json` の `hooks` にマージする。
   既に同じイベントの配列があるときは、置き換えずに要素として追加すること。
   **`command` の `node C:/claude/ClaudeCode/account-guard/account-guard.js` は作者の環境の
   パスなので、自分が `account-guard.js` を置いた場所に書き換えること。** パスを直し忘れると
   フックのプロセスが起動に失敗し、deny が一切出ないまま(= fail-open)保護が無効になる。
   しかもエラーが目に見える形では出ないので、`status` サブコマンドや下記の確認手順で
   実際に拒否されることを必ず確かめること。
   **`account-guard.js` を移すときは、同じディレクトリに `credentials.js` も一緒に置くこと。**
   ガードはこれを読んでアカウントを判別する。無いと判別不能として保護ツリーへの操作を
   すべて拒否するので、素通しにはならないが、許可されたアカウントで入っていても止まる。
3. 設定できたか確認する:

```console
$ node account-guard.js status
アカウント: pro
設定: C:\Users\<user>\.claude\account-guard\config.json
  C:/org-tree  allow=[team]  → 現在は 拒否
```

特定のディレクトリで拒否されるかを試すこともできる:

```console
$ node account-guard.js status C:/org-tree/some-project
判定(cwd=C:/org-tree/some-project): 拒否 — 作業ディレクトリが C:/org-tree 配下にあります
```

一時解除(後述の `guard unlock`)を使うなら `guard.cmd` も設置する。中では自分の置かれた
ディレクトリ(`%~dp0`)から `account-guard.js` を呼ぶので、**2 つを同じディレクトリに置いたまま**
PATH の通った場所に置けばよい(書き換えは要らない)。置かなくても `node account-guard.js unlock …` で同じことができるが、解除はユーザーが手で打つ
操作なので、短く叩ける形にしておくほうがよい。

## 拒否されたときの挙動

ツール呼び出しがブロックされ、理由が Claude とユーザーの双方に表示される。
許可されたアカウントに切り替えれば通るようになるが、順序を守ること。拒否の文面も同じ順序で
案内する: **先に `swap save` で現在のアカウントを退避してから** `swap <name>` で切り替える。
いきなり `/login` すると、まだ退避していないアカウントの認証情報はその時点で消える(後述の
`swap.js` を参照)。

切り替え先のアカウントを**まだ一度も退避していない**場合は、`swap <name>` が「退避されていません」で
止まる。この場合は初回セットアップと同じ順序 — `swap save <name>` で現在を退避 → `/login` で
切り替え先に入る → `swap save <別名>` でそちらも退避 — で進める。拒否の文面もこの順序を案内する。
禁じているのは `/login` そのものではなく、**退避より先に打つこと**。

ただし**作業ディレクトリが保護ツリーの内側にあるセッションからは、その `swap` 自体を実行できない**。
`swap` は Bash 経由の呼び出しになるので、cwd の判定に先に当たって同じ理由で拒否される。
コマンドの中で `cd` しても変わらない(判定に使うのはセッションの作業ディレクトリで、
コマンド文字列は見ていない)。この場合はツリーの外で開いた別のターミナルから打つこと。

保護ルールを設定していない状態では、このフックは**何も拒否しない**。
`status` で「保護ルール: なし」と出ていないか確認すること。

## 一時的に解除する (`guard unlock`)

一方のアカウントが使用量リミットに当たったとき、あるいは保護ツリーの中にあるが**実体は保護対象で
ない**ディレクトリを別アカウントで触りたいときに、**そのセッションに限って**保護を外せる。

```console
$ guard unlock "リミット回復まで tool-a を触る"          # いまの作業ディレクトリを解除
$ guard unlock --path C:/org-tree/tool-a "参照のため"    # 範囲を指定して解除
$ guard status                                            # 解除中の範囲を確認
$ guard lock                                              # 解除を取り消す
$ guard lock --path C:/org-tree/tool-a                    # 範囲を指定して取り消す
```

### Claude からの解除は止める

`guard unlock` は**ユーザーが `!` を付けて打つ操作**に限っている。Claude のツール呼び出しから
実行しようとすると拒否される。歯止めは 2 層:

- 引数に `guard`(または `account-guard`)と `unlock` の両方が現れたら拒否する。見るのは
  パスのフィールドしか持たないツール(`Read` / `Edit` / `Write` など、渡した値がコマンドとして
  実行されないもの)以外すべてで、シェルと委譲に加えて知らないツール(MCP のシェル実行系など)も
  含める
- 解除の状態ファイルと履歴(`~/.claude/account-guard/` 配下の `unlocks.json` と `unlock.log`)への
  書き込みを常に拒否する。1 つ目をすり抜けて**ファイルを直接書く**経路を塞ぐため。履歴も同じ
  扱いにするのは、この設計が「ユーザーが `!` で打った」ことに全体重を預けており、後から確かめる
  手掛かりが履歴しかないため(読み取りは止めない)。**ガードのディレクトリ自体を指す書き込みも
  同じく拒否する** ―― ファイル名の完全一致だけを見ていると、`cp <偽の状態ファイル>
  ~/.claude/account-guard/` のように受け側がファイル名を補う形で、名指しせずに置き換えられる。
  素通しするのは読み取り専用と分かっているツール(`Read` / `Glob` / `Grep`)だけで、それ以外は
  知らないツール(MCP のファイルシステムサーバなど)も含めて書き込みうるものとして扱う

PreToolUse フックはユーザーの `!` 実行では発火しないので、これで経路そのものが分かれる。承認
ダイアログ(`permissions.ask`)にしていないのは、押せば通る以上、もっともらしい理由を添えて
要求されたときに流し読みで通る余地が残るため。**解除中のセッションでも `guard unlock` は拒否
される** — Claude が解除を延長・再発行できると、範囲を絞って開けた意味がなくなる。

過剰検出は許容している。`grep "guard unlock" README.md` のような参照目的のコマンドも止まるが、
実害はその文字列を含むコマンドを打てないことだけで、必要ならユーザーが `!` で代行できる。
ガードのディレクトリを書き込み扱いにしたことで、**そのパスを言及しただけのコマンド**
(`ls ~/.claude/account-guard/`、パスを含むコミットメッセージなど)も同じく止まる。書き込みか
どうかはコマンドを解釈しないと分からず、解釈を増やすほど「その解釈から漏れた書き方」が
穴になるので、ここは拒否側に倒したままにする。読み取りだけなら `Read` / `Glob` / `Grep` を使う。
`guard lock`(安全側に戻す)と `guard status`(読むだけ)は Claude からも実行できる。

ただしどちらの層も**コマンド文字列とパスの照合**でしかない。呼び出しを間接化すれば ―― 実行内容を
別のファイルに置いてから起動する、パスを実行時に組み立てる ―― 判定に使える文字列が残らず、
機械的には止まらない。ここは「押し切られて解除する」「うっかり解除する」を止める境界であって、
回避しようとする相手を止める壁ではない。拒否の文面にも回避を試みないよう明記してあり、
実効性はその要請と、解除がユーザーの `!` 実行にしか現れないという運用に乗っている。

### 解除の単位はツリーではなくディレクトリ

`tree` は git の管理単位ではなくただのディレクトリパスなので、ツリー単位で解除する設計にすると、
ルートに保護対象と非保護対象が混在している構成で**全部が開いてしまう**。そこで解除の単位は
**ツリー配下の任意のディレクトリ**にしてある。既定は現在の作業ディレクトリで、兄弟ディレクトリは
保護されたまま。ツリー全体を開けたいときは `--path` にツリー自身を指定する(明示的な選択になる)。

拒否の原因ごとに、解除が効く条件は次のとおり。

| 拒否の原因 | 解除が効く条件 |
|---|---|
| 作業ディレクトリがツリー内 | その作業ディレクトリが解除範囲の配下 |
| 操作の対象がツリーを指す | **その対象が全部**解除範囲の配下 |

「全部」なのは、`tool-a` だけを解除した状態で `cp <tree>/tool-a/x <tree>/tool-b/` のように範囲外を
巻き込むコマンドが通る穴を塞ぐため。読み取りと書き込みは区別しない。

対象の切り出しがシェルの区切り以外で終わっているときも、解除の範囲内とは見なさない。
`<tree>/tool-a{,bc}` や `<tree>/tool-a[bc]` は展開してみるまで実際に触る場所が決まらず、
`tool-a` を解除していても兄弟の `tool-abc` に届きうるため。解除した範囲を素直に書けば通る。

### 決めごと

- **理由は必須。** 省略するとエラーになり、何も解除しない
- **`--path` はドライブ文字から始まる絶対パスだけ。** 設定の `tree` と違い、ドライブ文字を落とした
  形(`/org-tree`)は受け付けない。`tree` 側は広く一致しても拒否側に倒れるが(「設定」の項)、
  解除で同じ緩さがあると**保護が外れる向き**に広がるため
- **保護ツリーの外は解除できない。** 作業ディレクトリがどのツリーにも属さず `--path` も無いときは
  エラーになる。黙って全体を解除することはしない
- **知らないオプションはエラーになる。** 理由へ黙って混ぜない。`--paht` のような打ち間違いを
  理由として受け取ると、指定したつもりの範囲ではなく作業ディレクトリが開いてしまうため
- **有効期限は設けない。** セッションが終われば自動的に失効する。用途は「リミットが回復するまでの
  数時間」なので、短い期限は用途の途中で切れて再解除を促し、「とりあえず解除」を習慣化させる。
  歯止めのつもりが逆に効く
- **`cd` を含むコマンドは移動先も相対パスの基準にする。** `cd <dir> && cat ../x` のように移動して
  から相対で指す形を取りこぼさないため。区切りは `&&` `;` `|` だけでなく**改行も含む** ――
  複数行で書いた `cd` も同じ扱いになる。さらに**空白のあとに現れる `cd` も拾う**ので、
  `bash -c "cd .. && cat ../x"` や `eval`・`sudo` の内側に置いた `cd` も基準になる(ラッパーの
  名前を列挙する形だと、列挙から漏れた 1 つがそのまま抜け道になる)。**連鎖した `cd` は積み上げる**
  ―― `cd x && cd y` の基準は `x/y` で、`cd` ごとに元の作業ディレクトリから解決し直していた頃は
  この基準がどこにも無く、そこから登る相対パスが別の場所に解決されて解除の範囲内に見えていた
  (1 段なら拒否されるのに 2 段にすると通る、という段数だけで結論が変わる形だった)。実行順や
  条件分岐は追わないので、実際には通らない `cd` が混ざっていると、その移動先を基準にした解決まで
  判定に入る(過剰に拒否する側に倒れる)
- **ブレースを含むコマンドは展開した形も判定に入れる。** `cat C:/{org-tree,other}/x` のように
  ツリー名そのものが割れると、そのままでは連続したツリー名がどこにも現れず、拒否も解除の範囲
  判定も素通りするため。展開しきることは狙っておらず、単純な `{a,b}` を深さ 8 ・256 通りまで
  試すだけ。**上限で打ち切った場合は「対象を判定できなかった」として拒否する** ―― ツリー名が
  割れているときの判定材料は展開後の形だけなので、捨てた分を見ないままにすると選択肢を並べる
  だけで素通りできてしまう(上限を上げても同じ手が使えるので、拒否側に倒すしかない)。
  打ち切りを数えるのは **Bash だけ**。ブレース展開をするシェルは Bash であって PowerShell では
  なく、`@{x=1;y=2}` やパイプのスクリプトブロックまで数えると、ふつうのコマンドが判定不能扱いで
  拒否される。Bash 側でも、シェルが展開しないもの(JS / JSON のオブジェクトリテラル、jq の
  フィルタ)は**選択肢の中身の形**で見分けて数に入れない ―― どの選択肢にも引用符か空白が入って
  いれば展開されるブレースではない、と判断する。**引用符の中にあるかどうかでは見分けない**。
  `bash -c "... {a,b} ..."` の中身は内側のシェルが展開するので、引用符の中を落とすと、そこに
  選択肢を並べて上限を超えさせるだけで打ち切りが無印になり、割ったツリー名が素通りする
- **コマンドに実行時にしか決まらない要素(`$VAR` `${VAR}` `%VAR%` `$(...)` `` `...` `` `(...)`)が
  入ると、そのコマンドには一時解除を適用しない。** 触る場所が字面から決まらず、解除の範囲内で
  ある根拠が無いため。解除を入れる前と同じ「保護ツリーの中は無条件に拒否」に戻る(解除して
  いないセッションでは判定は変わらない)。**見るのはコマンド文字列全体**で、`cd` の移動先に
  限らない ―― 移動先だけを見ていた頃は `cat $(dirname ..)/tool-b/secret` が素通りしていた。
  とくに区切りを含まない `cat $X` はパスのトークンとして切り出されず対象が 1 つも作られない
  ので、実行時の値しだいで解除した範囲の外どこへでも届く。過剰拒否は承知のうえで、
  `git log --format=%H` のように実行時要素でない `%` を含むコマンドも解除中は止まる。パスを
  字面で書き直せば通り、書き直せないものはユーザーが `!` で打てる。
  `Read` / `Edit` / `Write` のようにパスのフィールドが決まっているツールは対象外(操作対象が
  そのフィールドに入っており、書き込む文面に `$VAR` があっても解除は失われない)
- 解除と取り消しは `~/.claude/account-guard/unlock.log` に履歴として追記される

解除が実際に効いた(本来なら拒否していた)ツール呼び出しでは、解除中である旨が Claude の文脈に
返る。毎回は出さない。範囲外のパスは従来どおり拒否される。

## アカウントを切り替える (`swap.js`)

ガードは「今のアカウントでは触るな」としか言わない。実際に切り替える側が `swap.js`。

`/login` はブラウザ OAuth を毎回踏む必要があるが、切り替えで実際に変わるのは
`~/.claude/.credentials.json` の 1 本だけで、CLAUDE.md・memory・skills・履歴は共有された
ままになる。それならファイルを退避して入れ替えるほうが速い、という判断
(比較検討は `docs/account-separation.md` §5.1)。

```console
$ swap                  # 現在のアカウントと退避済み一覧
現在のアカウント: pro  [pro から復元]
  C:\Users\<user>\.claude\.credentials.json  [残り 26 日]

退避済み (C:\Users\<user>\.claude\accounts):
* pro       [残り 26 日]
  team      [残り 12 日]

$ swap team             # 現在(pro)を退避してから team を復元
退避: pro
切り替え: pro -> team  [残り 12 日]

$ swap save             # 切り替えずに退避するだけ

$ swap warmup           # 退避済みアカウントの 5 時間枠をまとめて開ける
warmup: 次のアカウントの 5 時間枠を順に開きます
  team
  pro       [開始時のアカウント]
ping: ...\claude-window-keeper\claude-window-ping.ps1
終了時は pro に戻します。中断された場合は `swap pro` で戻せます。
続けますか? [y/N] y

--- team ---
退避: pro
切り替え: pro -> team  [残り 12 日]
(ping の出力がそのまま流れる)

--- pro ---
退避: team
切り替え: team -> pro  [残り 26 日]
(ping の出力がそのまま流れる)

結果:
  team: 成功
  pro: 成功
```

退避先は `~/.claude/accounts/<name>.json`。元の credentials と同じ ACL を継承させるため
`~/.claude` の下に置いている。平文トークンの本数は増えるが保護レベルは変わらない。
同じディレクトリの `.current` に「現在のログインがどのスロット由来か」を記録している
(一覧の `*` 印はこれ)。消しても壊れないが、消すと次の退避先を名前から推測することになる。
権限やロックで**読めない**場合も同じく推測に切り替わるが、黙って別名のスロットを作らないよう
その旨を知らせる。
既存の退避を上書きするときは、旧内容の控えを `accounts/.replaced/<name>-N.json` に残す
(スロットごとに 2 本まで。ただし落としてよいのは「失効済み」「同じ資格情報が他にも残っている」
と言えるものだけで、読めない控えは「復旧に使えない」と証明できないため上限を超えても残す。
どれでもない控えも同じく上限を超えたまま残す)。取り違えて上書きしても
`accounts/<name>.json` へ戻せば復旧できる。同じディレクトリの `.unreadable-current-N.json` は
「読めなかった現在の credentials」の控えで、復元には使えない(スロットへ戻さないこと)。
`swap` の status は両者を別の項目として表示する。`<name>.json.tmp` は書き込み中にプロセスごと
落ちたときに残る書きかけのファイルで、平文のトークンを含む。一覧にも控えの集計にも現れないため
status が別枠で知らせる(消してよいかは中身を見ないと決められないので、削除は促さない)。
同じことは切り替えの最終段でも起きるので、`accounts/` の外にある
`~/.claude/.credentials.json.tmp` も同じ枠で知らせる(場所が違うだけで、残るものは同じ
平文のトークン)。控えを取るとき、同じバイト列の控えが既に
あればそれを使い回すので、同じ壊れ方を繰り返しても控えは増えない
(読めない控えは上限の対象外なので、そうしないと際限なく積み上がる)。

`swap.cmd` は cmd / PowerShell から短く叩くためのラッパー。中では自分の置かれたディレクトリ
(`%~dp0`)から `swap.js` を呼ぶので、**2 つを同じディレクトリに置いたまま** PATH の通った場所に
置けばよい(書き換えは要らない)。
`swap.js` を別の場所へ移すときは `credentials.js` と `subcommands.js` も同じディレクトリへ
置くこと(前者はアカウントの読み方をガードと共有しており、後者はサブコマンド名の表を
故障注入テストと共有している)。置き忘れた場合は理由を示して止まる。

### 複数アカウントの窓をまとめて開ける (`swap warmup`)

5 時間枠を開けるための ping は**ログイン中のアカウントにしか打てない**(送信手段が `claude -p`
だけなので原理的にそうなる)。結果、片方だけが「5 時間おきの時刻表」に乗り、もう片方はどこにも
乗らない。作業を始める直前に全アカウントの窓を開けておけば、その時点から合計ぶんの作業が
穴なしで入る(背景は `docs/account-separation.md` §5.2)。`swap warmup` はその手順
——切り替えて ping、を人数分繰り返して元へ戻す——を 1 コマンドにしたもの。

- **不変条件は「終了時のアカウント = 開始時のアカウント」。** ping が失敗しても、途中で
  エラーが出ても守る。開始時のアカウントは順番の最後に回す。
- ping は `claude-window-keeper` の `claude-window-ping.ps1` を子プロセスとして呼ぶ。場所は
  環境変数 `CLAUDE_WINDOW_PING`、無ければ `swap.js` から見た
  `../claude-window-keeper/claude-window-ping.ps1`。**どちらも無い環境で使えなくなるのは
  `warmup` だけ**で、`swap` / `swap save` は今までどおり動く。
- `-Force` は付けない。5 時間未経過なら ping 側が SKIP するので、既に開いている窓に打つ枠の
  無駄を避けられる。SKIP かどうかを `warmup` 側では判定しない(ping の出力は素通しする)。
- `refreshToken` が無い・失効している・退避が読めないスロットは**スキップ**する。切り替えて
  から気づく形だと、更新できない認証にマシン全体を乗せた状態で次へ進むことになる。
  ただし判定するのは**退避から復元する対象だけ**。既にそのアカウントで動いている場合(退避が
  開始時の 1 件しかない、など)の認証は credentials 側にあり、退避ファイルは最後に `save` した
  時点の古いものでしかないので、そちらを見て弾くと有効な認証で開けるはずの窓を開けずに終わる。
- サブコマンドと同じ名前のスロット(`swap <name>` で復元できないもの)は除外し、理由を表示する。
- **既定で確認を取る。`--yes` で省略できる。** 標準入力が端末でなく `--yes` も無いときは中止する
  ——タイマーやフックから自動実行させないための歯止め(§5.2)。
- **`--force` は受け付けない。** `--force` は失効済み・判別不能・同一プランのガードをまとめて
  外すフラグで、`warmup` に付けると複数回行う切り替えのすべてに 1 回の同意で効いてしまう。
  特定のアカウントへ強行したいときは `swap <name> --force` を個別に実行する。
  ただし**開始時のアカウントへ戻る最後の 1 歩だけは内部で `--force` を使う**。付けないと
  `max → team → max` のような並びで最後の 1 歩が「同一プランで別アカウントだと証明できない」
  ガードに当たり、開始時とは別のアカウントに乗ったまま終わる。戻り先の退避はこの実行の最初の
  切り替えで `warmup` 自身が書いた内容そのもの(切り替えの前に必ず現在のログインを来歴の
  スロットへ退避するため)なので、ガードが守っている「別アカウントの取り違え」は起こりえない。
  進む向きの切り替えでは使わない。
- **来歴(`.current`)が未記録・読めないときは、切り替えを 1 回も行わずに中止する。** 戻り先の
  名前が決まらない状態では不変条件を守れないため。先に `swap save <名前>` で来歴を作ること。
- 子プロセス 1 つあたり 5 分でタイムアウトする。強制終了(Ctrl-C など)までは保証できないので、
  実行前に `swap <元の名前>` で戻せることを表示する。
- 失敗が 1 件でもあれば終了コードは 1。スキップだけなら 0(失効した退避を飛ばすのは仕様どおりの
  動作であって、失敗ではない)。

### 使う前に知っておくこと

- **一度も `save` していないアカウントには切り替えられない。** 初回は
  「いま入っているアカウントを `swap save` → `/login` でもう一方に入る → そちらも
  `swap save <名前>`」の順で通すこと。**先に `/login` してはいけない。** Claude Code が
  `.credentials.json` を置き換えるので、まだ退避していないアカウントの認証情報は
  その時点で消え、復旧にはブラウザ OAuth のやり直しが要る。
  2 回目の退避で**名前を明示する**のは、`/login` を挟むと来歴が前のアカウントを指したまま
  古くなるため。省略すると前のスロットを上書きしようとする(プラン種別が違えば別アカウントだと
  分かるので中止するが、同じプラン同士では判別できない)。
- **切り替えはマシン全体に即座に効く。** 稼働中の別セッションも次のリクエストから新しい
  アカウントになる。だからタイマーやフックから自動実行してはならない(`docs/account-separation.md` §1.3)。
- **アカウントの同一性は「証明できたこと」だけで判断する。** credentials に uuid や
  メールアドレスのような identity フィールドが無いので、中身から「誰のログインか」は分からない。
  使える材料は 3 つで、証明できる範囲が違う。
  (1) `refreshToken` の一致 = 同じ資格情報である証明、
  (2) `subscriptionType` の**不一致** = 同じアカウントの同じ世代ではないことの証明。
  別アカウントである証明にはならない(同じアカウントが Pro → Max と変わると、変更前に退避した
  スロットとは種別が食い違う)。一致のほうは何も証明しない。一致を同一と読むと、同一プランの
  別アカウントを取り違えて相手の唯一のバックアップを消す、
  (3) `.current`(来歴)= 前回このツールが書いた先の記録で、外から `/login` されたり
  書き込みが途中で落ちたりすると古くなるので、単独では上書きの根拠にしない。
  1 回の退避で書き込むのは、**名前で指定された 1 スロットだけ**。1 つのアカウントを 2 つの名前で
  退避していると片方が古いまま取り残されるが、そこを揃えて書き換えるには「旧内容と現在のログインが
  同じアカウント」だと言える必要があり、(1) の証明が無い限りそれは言えない。(3) を根拠にすると、
  同一プランの別アカウントを取り違えて、名前を挙げてもいないスロットまで巻き添えに潰す。
  取り残されうるスロットは書き換えず、退避のたびに名前を挙げて知らせる。ただし「古い」とは
  断定しない。現在のログインが同じアカウントの新しい世代なのか、別アカウントへ `/login` した
  結果なのかは見分けられず、後者に更新を勧めると相手の唯一のバックアップを潰すため
  (初回手順の 2 回目の退避がまさにこれに当たる)。同じアカウントの更新だと分かっているときだけ
  `swap save <name> --force`。この信号は `swap` の一覧にも `[現在のログインと内容が違います]`
  として残るが、付くのは**来歴が指すスロットの内容が現在のログインと食い違う場合に限られる**。
  同じアカウントを複数の名前で退避している場合、来歴が指していない側には印が付かず、
  退避のたびに出る一過性の警告(押し出したときの表示)を見逃すと後から気づく手段が無い
  (`.replaced` の控えは「かつて押し出された内容」の証明にしかならず、「いまどのスロットが
  古いか」の判定には使えないため、一覧の印には使っていない)。
  退避名の既定値(名前を省略したとき)は、来歴が無ければ `subscriptionType` から作る。
  スロット名にサブコマンドと同じ語(`save` / `help` など)は使えない。作れてしまうと
  `swap <name>` がサブコマンドとして解釈され、そのスロットを復元する手段が無くなるため。
  ただし**既にあるスロットへの退避は止めない**。止めても復元手段は増えないうえ、来歴が
  その名前を指している間は切り替えそのものができなくなる(退避は切り替えの前段にある)。
  その代わり、案内としても `swap <name>` を出さない。打てば復元ではなくサブコマンドが走り、
  切り替わっていないのに exit 0 で終わる(ラッパーからは成功に見える)ため、status の
  「復元できない名前の退避があります」と同じく改名を促す。
- **既存スロットを別の認証情報で上書きしようとすると中止する。** `swap save team` の打ち間違いなどで、
  そのアカウントの唯一のバックアップが消えるのを防ぐため。同じアカウントだと分かっているなら
  `swap save <name> --force`。同一プラン同士は原理的に判別できないので、そこは判断ではなく構造で守る。
  上書きの前に旧内容を `accounts/.replaced/` へ控えるので、取り違えても改名で戻せる
  （控えはスロットごとに 2 本までだが、他に複製が残っていると言えない控えは上限を超えても残す。
  本数のために唯一の 1 本を消しては本末転倒なので）。
- **切り替えが起きなかったときは終了コードを成功にしない。** 「すでにそのスロットから復元した
  状態」で認証を変えなかった場合など、要求された切り替えが起きていない経路は非ゼロで終わる。
  `swap team && claude -p ...` のようなラッパーが、別のアカウントのまま次の処理へ進まないため。
- **`--force` の意味は退避側と復元側で別。** `swap <name> --force` は復元側の判断
  （失効済み・`subscriptionType` 無し・同一プランでも復元する、現在の credentials が読めなくても
  控えを残して進む）で、**退避先に別のアカウントが入っていれば、それでも中止する**。
  スロットを上書きしてよいという明示は `swap save <name> --force` だけ。1 つの旗にまとめると、
  復元の都合で付けた `--force` が、退避名（プラン種別由来のことがある）に当たった無関係の
  スロットを黙って潰す。
- **復元先が「別アカウント」だと証明できないときは切り替えを中止する。** 同一プラン（または
  プラン種別を読めない）の相手は、別アカウントなのか自分の古い退避なのか判別できない。後者だと
  ローテート前のトークンに戻り、稼働中のセッションが次のリクエストで認証エラーになる。
  来歴の有無では判断を変えない（来歴が語るのは現在のログインの出どころだけで、復元先が何者かは
  何も証明しない）。別アカウントだと分かっているなら `swap <name> --force`。
- **`refreshToken` には有効期限がある。** 失効済みのものを復元しても `/login` のやり直しに
  なるだけなので、切り替えは**実行前に中止する**。失効が近いものは一覧の残り日数で分かる。
  `refreshToken` を持たない中身(手で編集した退避、将来の構造変更)も同じ扱いで中止する。
  復元しても認証を更新できず、`accessToken` が切れた数時間後にマシン全体が認証エラーになるため
  (一覧では `[refreshToken がありません]` と出る)。
- **`subscriptionType` を持たない中身は復元しない。** 復元するとガードが誰のログインか判別できず、
  保護ツリーへの操作がすべて拒否される。元に戻す操作まで巻き添えになるので手前で止める。
- 復元先のファイルは書き換える前に検証する。壊れたファイルで現在のログインを潰すことはない。
  現在の credentials が読めないとき(破損している、他のプロセスが書き込み中、権限が無い)も、
  退避できない以上は切り替えを中止する。**ただし中止したまま抜け出せなくなっては安全ではないので、
  `--force` を付ければ切り替えられる**。読めない中身はスロットには入れず(復元に使えないうえ、
  そこにある有効な退避を潰してしまう)、`accounts/.replaced/` に控えとしてだけ残す。
- **切り替えた直後の使用量ログは 1 行だけ混ざりうる。** `usage-tracker/collect.js` は同じ
  `.credentials.json` でアカウントを判定するため、切り替え後の最初の描画は「新しいアカウント名 +
  切り替え前のレスポンス由来の残量」になる。枠の集計を厳密に見るときは切り替え時刻の前後を
  疑うこと(collect 側での対処は未着手)。
